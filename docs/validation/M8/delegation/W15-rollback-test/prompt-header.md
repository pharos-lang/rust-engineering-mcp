## Decisión D12 §6 (`docs/validation/M8/03.md`)

Probar una vez, con binarios reales, sobre estado real:
(a) journal pendiente `analyzer_action_apply` escrito por **0.8.0** → **0.3.0** `mutation list --state-root … --json` falla cerrado (`RecoveryRequired`/kind desconocido), sin tocar el journal;
(b) estado M3 (`quality-artifacts`) y catálogo SQLite escritos por 0.8.0 → 0.3.0 los lee (`quality-artifacts recover --json`, `catalog status --json`);
(c) floor de secuencia del bundle de confianza avanzado por 0.8.0 (`catalog import` de un bundle firmado de secuencia N) → 0.3.0 rechaza un bundle de secuencia N-1 (floor no retrocede) y acepta el estado;
(d) estado escrito por 0.3.0 → 0.8.0 lo lee (upgrade) y `doctor` lo valida.

## Cómo

1. **Driver `scripts/test-m8-rollback.py`** (reglas Sonar: rutas desde `ROOT`, sin `/tmp` literal — usa `tempfile` bajo `target/`, sin `type=` en argparse, sin `shell=True`): `--old-tag v0.3.0` (por defecto) construye el binario antiguo en un `git worktree` bajo `target/m8-rollback/worktree-<tag>` con `cargo build --release --locked --offline --target-dir target/m8-rollback/target-<tag>` (el lock de `v0.3.0` fija las mismas dependencias; si `--offline` falla por una dependencia ausente, **para y repórtalo**, no descargues). Verifica `version --json` de ambos binarios (0.3.0 / 0.8.0). Luego ejecuta los escenarios (a)–(d) con `subprocess` sobre `state-root`/`catalog-store`/`catalog-trust` temporales, comparando salidas JSON y exit codes, y escribe el recibo `docs/validation/M8/03-rollback.json` (`format_version 1`, `generated_utc`, `head_commit`, `old_tag`, `old_commit`, hashes sha256 de ambos binarios, escenarios con comando, exit code, extracto de salida, `status`; `status` global `passed` solo si los cuatro pasan; nada que no corrió se marca `passed`).
2. **Cómo producir el estado**: para (a) necesitas un journal pendiente con kind `analyzer_action_apply` sin Docker: escribe un test nativo `#[ignore]` en `crates/project-adapter/tests/rollback_native.rs` que, con env `RUST_MCP_ROLLBACK_STATE_ROOT`, use el API del store M2 (mira `tests/support/native_mutation.rs` y cómo los tests M6 crean planes `MutationKind::AnalyzerActionApply`) para dejar un journal en fase no terminal; el driver lo invoca con `cargo test -p rust-engineering-project --locked --offline --test rollback_native -- --ignored`. Para (b) usa el CLI 0.8.0 (`quality-artifacts`, `catalog import` con el bundle firmado de fixtures que ya usan los tests de catálogo — localízalo en `fixtures/` o `crates/catalog-adapter/tests`; si el bundle de fixtures no tiene dos secuencias, genera el segundo con las utilidades de test existentes (clave pública de prueba) y documenta cómo). Para (c) importa N con 0.8.0 y luego intenta N-1 con 0.3.0. Para (d) crea estado con 0.3.0 y léelo con 0.8.0 + `doctor --json`.
3. **`scripts/test-m8-rollback-unit.py`**: tests herméticos del driver (parseo de salidas, composición del recibo, decisión `passed/failed`, ningún `git`/`cargo` real: dobles).
4. Ejecuta el driver **una vez** de verdad (foreground; la construcción de 0.3.0 puede tardar 10–20 min: usa un `timeout` amplio en tu llamada, no segundo plano) y deja el recibo. Si un escenario no puede ejecutarse (p. ej. no hay bundle con dos secuencias), márcalo `unavailable` con el motivo — nunca `passed`.
