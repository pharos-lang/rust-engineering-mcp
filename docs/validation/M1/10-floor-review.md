## Method and scope

Read-only analysis of the supplied text only. No tools, commands, or writes were used. `bundle.rs`, `catalog_semantic.rs`, and `catalog_sync.rs` were not provided, so findings that depend on them are stated with explicit preconditions rather than asserted.

## P0

None. Within the stated threat model (host-provisioned 0700 store, same-uid attacker and deliberate owner deletion out of scope, ACLs excluded, macOS 26/APFS only), I found no path that activates a sequence below the retained floor, and no path that discards the floor while accepting a bundle. The monotonicity ladder in `catalog_cli.rs:198-208` + `:256-261` is sound — see "Verified" below.

## P1

**P1-1 — `Floor::new` writes fields that `Floor::parse` will later reject; a valid signed bundle can permanently brick a store.**
`floor.rs:16-27` constructs the record from `bundle.manifest()` with no validation, while `floor.rs:39-51` rejects `sequence == 0`, `sequence > i64::MAX`, a `bundle_sha256` that is not 64 lowercase hex, and any `publisher`/`channel` differing from the *trust file*. Preconditions for the brick: (a) `bundle::verify` admits `manifest.sequence == 0` or `> i64::MAX`, or (b) `bundle::verify` authenticates the signature/key without also enforcing `manifest.publisher == trust.publisher && manifest.channel == trust.channel`. Under either, `catalog_cli.rs:269` reserves a floor that `catalog_cli.rs:194-197` will fail to parse on the *next* invocation, and every subsequent `status`/`import`/`rebuild-index` returns `CATALOG_STATE_INVALID` with no recovery path that does not delete trusted state — directly contradicting the remediation text at `catalog_cli.rs:306-309`. Fix: validate the same predicates in `Floor::new` (or reuse `parse` on the freshly serialized bytes) and fail the import *before* `reserve_floor`, so the store is never left unparseable. This is cheap and removes the dependency on an unaudited invariant in `bundle.rs`.

**P1-2 — `CatalogStatus` exposes no floor state; an active generation behind its floor is reported as `passed` with no signal.**
`catalog_cli.rs:117-129` and `:150-166` report only the active bundle's sequence. `catalog_cli.rs:203-207` deliberately permits `active.sequence < floor.sequence`, and the test at `catalog_cli.rs:168-170` codifies that `status` then prints `sequence: 1` while the floor holds 2, exit 0. Two distinct conditions are indistinguishable to an operator: an interrupted reservation (benign, ADR-041:67-68) and a same-uid or restore-based downgrade of `active.bundle` to an older validly signed generation (which the floor blocks on *import* but never on *read*). ADR-041:76-77 instructs callers to "reread status after uncertain commit", but status cannot answer the question it is being reread for. Fix: add `floor_sequence` (and ideally `floor_bundle_sha256` / a `reservation_pending: bool`) to `CatalogStatus`, and have the non-JSON branch at `catalog_cli.rs:426` print it. Precondition for exploitation: attacker or restore with write access to the store directory — nominally out of scope, but the detection gap is in scope because the ADR claims post-crash observability.

**P1-3 — Key rotation makes the documented recovery instruction unachievable, and the error path does not distinguish it.**
`floor.rs:37-55` binds the floor to publisher/channel only, so rotation preserves the sequence (correct, matches ADR-041:21-22). But when the active record was signed by the retired key, `bundle::verify` fails, `catalog_cli.rs:211-215` (status) and `:277-282` (rebuild) return `Error::State`, and the message at `catalog_cli.rs:306-309` tells the operator to import "an authenticated exact reserved or newer generation". The exact reserved container is precisely the one that can no longer verify; only a strictly newer bundle works. Preconditions: rotation performed while `active.bundle` is at `floor.sequence`. Impact is operational, not a bypass — `floor.permits` at `floor.rs:62-64` correctly refuses anything at or below the floor from the new key. Fix: separate `Error::State` into "active unverifiable under current trust" vs "floor invalid", and give the former a message that names strictly-newer-sequence as the only remedy.

**P1-4 — Trust-file publisher/channel change is an unrecoverable fail-closed state even with no active record.**
`catalog_cli.rs:194-197` parses the floor against the new trust config before any consideration of whether an active record exists; `floor.rs:40-41` then rejects on publisher/channel mismatch. So renaming a channel in the trust file bricks a store that is otherwise empty of an active bundle. ADR-041:44-45 only commits to failing closed "beside an existing active record"; the implementation is stricter than the ADR. Either tighten the ADR wording or, more usefully, report a distinct error code (e.g. `CATALOG_TRUST_MISMATCH`) so an operator can tell "your floor is corrupt" from "your floor belongs to another publisher/channel".

## P2

**P2-1 — Non-empty `store.lock` yields `LimitExceeded`, surfaced as a budget error.** `catalog_store.rs:435` and `:460-461` call `stamp(..., 0, true)`, which returns `LimitExceeded` for any `st_size > 0` (`:124-126`). A single stray byte in the lock file makes every operation fail as `OUTPUT_LIMIT_EXCEEDED` / "Catalog acquisition or validation exceeded its budget" (`catalog_cli.rs:338-341`), which points the operator at the wrong thing. Prefer a dedicated check with `Denied`/`Changed`.

**P2-2 — Corrupt-floor fail-closed is only tested for the JSON-invalid case.** `catalog_cli.rs` test at `:125-129` covers garbage bytes. An oversized (>4 KiB) or symlinked `floor.record` is covered only at the store layer (`tests/catalog_store.rs:391-419`) and reaches the CLI as `OUTPUT_LIMIT_EXCEEDED` / `SANDBOX_DENIED`, not `CATALOG_STATE_INVALID`. The claim "corrupt floor beside active fails closed" is true, but the observable contract varies by corruption mode. Add CLI cases and, if the contract matters, normalize floor-read failures to `CATALOG_STATE_INVALID`.

**P2-3 — `reserve_floor` enforces no monotonicity at the store layer.** `catalog_store.rs:508-510` writes whatever bytes it is given; the invariant lives entirely in `catalog_cli.rs:259-261`. That is defensible layering (documented at `:506-507`), but the ADR's read-only runtime acquisition path (ADR-041:55) will be a second caller. Consider a debug assertion or a typed `FloorBytes` newtype so a future caller cannot lower it silently.

**P2-4 — `--store` and `--index-store` are not checked for equality.** `catalog_cli.rs:291` opens a second `CatalogStore` while the first lease is held; if the paths are equal, `index_store.commit` at `:294` would overwrite the catalog's `active.bundle` with derived index bytes. In practice the flock at `catalog_store.rs:436-442` is per open-file-description and returns `Busy` first, so the destructive case is blocked — but only incidentally, and the operator sees "Another catalog operation holds the store lock" for what is actually an argument error. Reject equality in `parse` (`:82-94`).

**P2-5 — `semantic_index_available` conflates two checks.** At `catalog_cli.rs:217-232`, when both `--model-dir` and `--index-store` are given, the `validate_imported_index` result is computed then unconditionally overwritten by `validate_persisted_index`. Only the second is reported, under one field name. Either name the two conditions separately or skip the first computation.

**P2-6 — `status` mutates the store.** `CatalogStore::open` unconditionally unlinks both staging names and fsyncs the directory (`catalog_store.rs:451-454`), so a read-only-looking `status` takes an exclusive lock and writes. Acknowledged as intended for the CLI; the risk is entirely in the future runtime path, which must not reuse `CatalogStore::open`. Worth an explicit `#[doc]` warning on `open` rather than only the prose at `:385-387`.

## Verified correct (no action)

- **Monotonicity ladder.** With a healthy active, `require_newer_than` (`catalog_cli.rs:256-258`) rejects equal and lower. With floor ahead of active after an interrupted reservation, `permits` (`floor.rs:62-64`) admits only the exact reserved container hash at the equal sequence, or strictly newer — matching ADR-041:41-43. Equal-sequence substitution with a different signed container is caught at `catalog_cli.rs:203-207`. No path lowers the floor.
- **Ordering and atomicity.** `reserve_floor` fully durably precedes `commit` (`catalog_cli.rs:269-270`); `replace_record` fsyncs + `fcntl_fullfsync` on the staging file before rename (`catalog_store.rs:548-549`), and every post-rename failure collapses to `DurabilityUncertain` without undo (`:569-584`). The readback at `catalog_cli.rs:271-274` is a genuine end-to-end check, not a cache read, since `read_active` re-opens through the pinned directory fd.
- **No implicit floor reconstruction.** `catalog_cli.rs:198-200` fails closed on missing floor with present active; nothing writes a floor except after a candidate has verified.
- **Staging is never promoted**, including when active is absent (`catalog_store.rs:451-453`), and a `Busy` open does not clear another import's staging (test at `tests/catalog_store.rs:123-130`).
- **Trust ancestor chain.** Resolution always restarts from the retained `/` fd (`catalog_store.rs:342-343`), held-vs-current inode equality is enforced on both descriptors (`:365-369`), and the sticky exception is pinned to the literal relative path `private/tmp` with `uid == 0 && mode == 0o1777` plus a mandatory private immediate child (`:315-324`, `:352-354`).

The documented limits you listed — POSIX-only checks with no ACL parser, cooperative rather than hard I/O deadlines, no same-uid/admin rollback guarantee, APFS/macOS 26 only — are consistently reflected in the code and comments (`catalog_store.rs:54`, `:246-248`, `:600-603`, ADR-041:108-112) and I found no place where the implementation claims more than that.
