## Pruebas discriminantes

`crates/mcp-server/tests/protocol.rs` ejecuta el binario construido por Cargo con
entorno limpio salvo `RUST_LOG=trace` adverso; no usa modelos rmcp como oráculo.
El harness tiene deadlines de 10 segundos por operación, captura acotada de stdout
y stderr y guard kill/wait del proceso ante error o assertion.

- Discovery y tools/list modernos: identidad/versiones/capability exactas,
  resultType complete, lista vacía sin cursor y determinismo.
- Bootstrap directo con tools/list; cuatro versiones legacy y fallback de
  initialize que solicita versión moderna o desconocida.
- Metadata ausente/malformada antes/después de bootstrap; -32022 recuperable
  incluso en el primer request. No se endurece arbitrariamente el lifecycle SDK.
- tools/call no implementado, método desconocido con contenido sensible y
  cancelación de ID desconocido; sin reflejos en logs ni respuestas espurias.
- EOF vacío y con requests completos pendientes; EOF con frame incompleto rechazado.
- Reads fragmentados, CRLF y requests agrupados con IDs correlacionados.
- JSON sintácticamente inválido ignorado; formas inválidas con -32600 sin ID;
  recuperación con siguiente request válido.
- Límite exacto de 1 MiB repetido por sesión, CR contabilizado, exceso con/sin LF;
  salida 1 sin esperar EOF y diagnóstico constante sin payload.
- Stdout cerrado antes/después de bootstrap, stdin abierto: salida 1. El fixture
  Unix cierra todos los handles del peer; shutdown solo no produce EPIPE en macOS.

Los ocho tests CLI verifican modos soportados, rechazo de argumentos sobrantes,
argumentos no UTF-8 y fallos de escritura. Los 21 tests y el doctest de dominio
preservan los contratos M0-02.

| Finding / observación | Resolución del principal |
| --- | --- |
| Medium 1: API rmcp no verificable por Claude en el paquete | Check independiente del worker sobre adapter final y fuente fijada, registrado abajo; los tests wire prueban además el dispatch real de unknown methods, discovery y negociación. |
| Low 2: exigir ausencia de respuesta al coalescer línea válida y oversized | No se adopta esa expectativa: un write del cliente no equivale a un read del servidor. Con chunks de 8 KiB y límite de 1 MiB, el prefijo válido puede procesarse antes de detectar exceso. El contrato es cierre de sesión sin garantía para requests pendientes; no garantiza descartar todo el write. La prueba propuesta sería incorrecta/dependiente del scheduling. |
| Low 3: subscriber local ligado a runtime current-thread | Comentario local incorporado; no se cambia a estado global innecesario. |
| Low 4: cargo-deny/licencias transitivas | Se mantiene gate de licencia/distribución antes de release. No se inventa policy del owner; cargo audit sí evaluó todo el lockfile. |
| Tokio io-std indirecto | El adapter llama `rmcp::transport::stdio`; la feature explícita `rmcp/transport-io` habilita su implementación e io-std. El binario no usa directamente `tokio::io::stdin/stdout`; no falta feature requerida por su API. |
| ID omitido en Invalid Request | Comportamiento del SDK fijado y testado; no se modifica el protocolo en el adapter. La matriz no afirma conformidad completa de JSON-RPC para cada versión legacy. |
| 100 ms de shutdown | Acota la espera del runtime una vez termina el servicio; no es deadline de requests ni garantía de cleanup de procesos. No hay children/operaciones de dominio en este corte. |
| Reader I/O error sin fixture específico | Mejora opcional; EOF parcial, exceso y errores reales de writer cubren los fallos exigidos aquí. No se atribuye cobertura de errores del OS no probados. |

### Check independiente del SDK fijado

Worker de investigación Sol Medium, read-only, comparó el adapter del commit
`0d6dfc0` con `rmcp-3.2.0` de la cache del registry, versión/checksum fijados en
Cargo.lock. Resultado: **sin discrepancias de API o semántica**. Referencias exactas
relativas a `rmcp-3.2.0/src/`:

| Uso del adapter | Evidencia en el SDK |
| --- | --- |
| `on_custom_request -> Result<CustomResult, ErrorData>` | `handler/server.rs:506-510`; alias ErrorData en línea 6; dispatch CustomRequest en `223-226` |
| `ServerInfo::new` / `with_server_info` | `model.rs:1056-1064,1073-1076`; alias ServerInfo en `1087` |
| Lista explícita de versiones | `handler/server.rs:64-71,346-353`; negociación legacy `service/server.rs:479-510,653-658` |
| Cancelación durante bootstrap y loop | `service/server.rs:445-459`; `service.rs:1436-1438` |
| Reader error convertido por SDK en None | `transport/async_rw.rs:142-144`; `service/server.rs:439-442`; `service.rs:1400-1406` |
| Cierre del writer | `transport/async_rw.rs:199-202`: drop del writer, no llamada prometida a poll_shutdown |

El flag `IoFailure` conserva la distinción entre EOF y fallo aunque el SDK los
represente igual. La cancelación se marca después del fallo; la condición final
impide exit 0 por la rama de EOF/cierre en esa carrera.
