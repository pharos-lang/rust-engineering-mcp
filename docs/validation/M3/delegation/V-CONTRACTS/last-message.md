| F1 | **P1** | `crates/mcp-server/src/stdio/coverage.rs:275-291` | `rust.coverage` implements its own execution-mode gate instead of reusing `nextest::select_execution_mode` | An explicit `execution_mode:"task"` request is routed through `matches!(mode, ExecutionMode::Task) → self.blocked(Code::SandboxDenied, …)`, which returns a **structured `isError:true` tool result**. ADR-060 §"Negotiation and synchronous fallback" is explicit: `task`'s absence-of-capability case "returns fixed `-32602` with no data, before worker admission, reservation or work." All three sibling M3-01/04/05 tools (`nextest.rs`, `semver.rs`, `mutation_test.rs`) implement this correctly by calling the shared `select_execution_mode`, which returns `Err(ErrorData::invalid_params(TASKS_REQUIRED, None))` for exactly this case — a protocol-level `-32602`. `rust.coverage` alone diverges, producing a different wire shape for an identical request pattern across sibling M3 tools, and is a regression from the ADR-060 decision that V06/V17/V18 already reviewed and accepted. | Route `execution_mode` handling in `coverage.rs` through `nextest::select_execution_mode` (already used by `semver.rs`/`mutation_test.rs`) instead of the ad hoc `if`/`matches!` block, so `Task` requests return `Err(ErrorData::invalid_params(TASKS_REQUIRED, None))` identically to the other three tools. |
| F2 | **P1** | `crates/mcp-server/src/stdio/coverage.rs:130-138, 276-285` | The `auto`-mode-exceeds-synchronous-budget case reports `error_code: Code::SandboxDenied` | ADR-060 mandates: "A long or unqualified operation returns a structured `isError` result with closed remediation code **`TASKS_REQUIRED`**." `SandboxDenied` is a distinct, pre-existing operational code meaning host-policy/capacity denial (busy, calibration failure), not "this call needs Tasks." Coverage's `Code` enum (`ProjectNotFound, InvalidProject, CommandTimeout, OutputLimitExceeded, SandboxDenied`) doesn't even define a `TasksRequired` variant, unlike the sibling tools' `Code` enums which all include it. A caller cannot distinguish "coverage is temporarily busy/denied" from "this call needs Tasks; retry synchronous ≤60s or use Tasks" — exactly the ambiguity the closed-taxonomy rule (G1) exists to prevent, and it silently disagrees with `docs/tools.md`'s and the ADR's own remediation contract. | Add `TasksRequired` (and `ToolNotInstalled`, see F3) to coverage's `Code` enum and emit it for the auto-exceeds-budget path, matching nextest/semver/mutation_test. |
| F3 | P2 | `crates/mcp-server/src/stdio/coverage.rs:119-123, 396-399` | `Outcome::Unavailable { error_code: &'static str, … }` uses a raw string (`"TOOL_NOT_INSTALLED"`) instead of a closed enum | Every sibling M3 tool's `Unavailable` variant uses `error_code: Code` (a closed, schema-enumerated type). Coverage's own `Code` enum doesn't include a `ToolNotInstalled` member, so the author fell back to a free-form `&'static str` field. This is precisely the "no free-form strings where an enum belongs" defect the review brief calls out: the generated output JSON Schema for this field is an unconstrained string, not a closed enum, breaking schema-closure symmetry with the other three tools' identical outcome shape and with G1's DTO-closure rule. | Extend coverage's `Code` enum with `ToolNotInstalled` and change `Unavailable.error_code` to `Code`, matching the other three tools' shape exactly. |
| F4 | P2 | `crates/mcp-server/tests/protocol.rs` (whole file) | No dedicated protocol test exists for `rust.coverage`'s `execution_mode`/`TASKS_REQUIRED`/task-rejection gate | `nextest_contract_and_synchronous_gate_are_stable_in_all_wire_versions` (line 1300), `semver_contract_and_synchronous_gate_are_stable_in_all_wire_versions` (line 1363) and `mutation_test_contract_and_task_gate_are_stable_in_all_wire_versions` (line 1442) each exercise the full five-version × `auto`/`synchronous`/`task` matrix and assert `TASKS_REQUIRED` / `-32602`. No equivalent function exists for `rust.coverage`; coverage's only test is the unrelated `rejects_package_workspace_contradiction` in `coverage.rs`'s own `#[cfg(test)]` module, plus a schema-snapshot equality check (protocol.rs:404) that only compares the static tool definition, never invokes it. This is exactly why F1/F2 shipped undetected — the discriminating oracle the roadmap requires ("five negotiated protocol versions covered for each new tool") does not exist for this tool. | Add a `coverage_contract_and_synchronous_gate_are_stable_in_all_wire_versions` test mirroring the other three, asserting `TASKS_REQUIRED` for default `auto`, `-32602` for explicit `task`, and `PROJECT_NOT_FOUND` for a qualified `synchronous` call, across all five protocol versions. |
| F5 | P2/doc | `docs/tools.md:866-889` vs `docs/validation/M3-matrix.md:4,11` and ADR-062 "Open issues" | `docs/tools.md`'s `rust.coverage` section describes a fully working two-phase capture/report/artifact flow with no caveat | The project's own validation matrix records coverage as **"Blocked (containment)"**: "el primer oracle real termina 101 porque el volumen persistente aprobado es `noexec` y niega ejecutar el test compilado… 0/1 seleccionada y siete no ejecutadas." ADR-062's Open Issues section states this is unresolved and "M3-03 remains fail-closed pending an orchestrator-approved shape." AGENTS.md requires `docs/tools.md` to reflect "una limitación operativa... que afecte a usuarios" in the same change. As written, a reader of `docs/tools.md` has no way to know that, in the currently approved image, every real `rust.coverage` invocation is expected to fail with a bounded/blocked result rather than ever reaching `Passed`. | Add an explicit caveat to `docs/tools.md`'s `rust.coverage` section (or a pointer to `docs/validation/M3-03.md`) stating the current containment-boundary limitation, consistent with how the tool's own in-code description already undersells versus the ADR's Open Issues. |

## 5) Missing contract tests

- No test asserts coverage's `Unavailable.error_code` is schema-constrained (would have caught F3).
- Not verified in this pass (recommend a follow-up): D06-T01–T15 discriminating tests from ADR-060 (task masking, cross-ProjectRef/grant, non-delivery orphan window, 16-suppressed-response interaction) — `tasks.rs` and its `#[cfg(test)] mod tests` were read only at the dispatch level, not exhaustively matched against each D06-T* item.

## 6) Limitations of this review
Given the size of the object (4 tools + DTOs + Resources + Tasks + snapshots + docs across ADR-060/061/062/063/064), this pass concentrated on cross-tool contract consistency (the four tools' `execution_mode`/error-taxonomy symmetry) and the coverage-tool/doc/ADR triad, since that is where a concrete, reproducible divergence was found. I did not do a line-by-line audit of `contract.rs`, `resources.rs`, the `quality_artifact`/`job` domain/application modules, or the ADR-060 D06-T* test matrix against `tasks.rs`; I also did not verify byte-identity of the 18 M1/M2 snapshots beyond confirming the test harness's own comparison logic exists and runs (`protocol.rs:385-412`) — I did not diff snapshot file contents against a pre-M3 git revision myself.
