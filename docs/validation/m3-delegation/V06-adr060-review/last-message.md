## 1) Verdict

**Revise.** The decision is architecturally sound and the SDK claims it rests on are accurate against the pinned source, but there are multiple P2 defects: an orphan rule that will cancel legitimately delivered jobs, an inaccurate SDK constraint used to justify unconditional capability advertisement, an internally incoherent budget table (fails G3's "unidad/fase/default/máximo/exceso" rule on arithmetic), an undefined relationship between the new job permit and ADR-030's single worker slot, an unstated cancellation-token hazard that would abort every task-mode job at creation, and two spike gaps/flakiness risks.

## 4) Contradictions with normative sources / sibling drafts

1. **G3 (`m2-m8.md:105-106`)** — "Cada nuevo límite se fija … con unidad, fase cubierta, valor por defecto/máximo y prueba del exceso": the table has all five columns but the values do not compose (F03) and four rows have no exceed test (F13).
2. **L08 / ADR-030 (`traceability:58`, `ADR-030:20-26`)** — one active worker, permit held until the blocking closure exits: the ADR introduces a second permit concept without reconciling it with the existing slot, and without stating the starvation consequence for the other 18 tools and for Resource reads (F04).
3. **ADR-030:48-50 / L10** — "cancel suprime respuesta conservando slot; Tasks M3-02 no libera antes cleanup": the ADR honours this (it never recycles the retained lease), but derives from it a *blind* 30 s orphan rule even though the product's own transport observes send completion (F01).
4. **ADR-061:116-132** — `owner_binding` explicitly excludes a session principal; ADR-060's `JobOwner` requires one (F10). Identifier prefixes also diverge (F12).
5. **ADR-061:153 vs ADR-060:239** — 1 h artifact TTL (host-raisable to 24 h) vs fixed 2 h record TTL, with no rule for dangling references (F11).
6. **`m3-quality.md:43-54`** — D06 must "verificar API exacta … antes de anunciarla" and contrast L09/L10. The API verification is done and accurate; the *client* side of "antes de anunciarla" is not: the advertisement flip is gated only on product-handler qualification, not on the G4 client matrix (F02, F07).

Not contradictions (checked and confirmed consistent): the masked fixed `-32602 task unavailable` with no data and no identifier echo matches existing policy (`contract.rs:84-86` fixed `-32602` with `data: None`; `resources.rs:40-42` one fixed `resource_not_found` for malformed/absent/foreign) and matches SEP-2663's mandated code; `auto → synchronous only for a qualified short operation, else reject` is verbatim the roadmap rule (`m3-quality.md:46-54`), as are the 60 s/120 s sync figures and the 300 s/3600 s job figures; "no notification promise" is correct (`rmcp service/server.rs:238-247`); "no `tasks/result`/`tasks/list`", `-32021`, `ttlMs: null`, cooperative cancel, ID-echoing `unknown_task` (`task_manager.rs:540-541`), opportunistic sweeps and abort-at-expiry are all confirmed against the pinned source, so the "do not wrap `TaskManager`" rationale holds.

## 6) Limitations

- Read-only: I did not compile or run the spike; the "5/5 passing" claim is unverified. My flakiness analysis (F08) is static, derived from `sweep_expired` semantics plus the 500 ms TTLs and 2 s timeouts.
- Dependency/leak check for the spike is static: it adds no `Cargo.toml` entry, spawns no process and opens no file/socket (in-process `tokio::io::duplex` only); it relies on `tokio`'s `sync` feature, which the workspace does not list (`Cargo.toml:46`) but which is already unified in by rmcp and used by existing tests — so it compiles, but through an implicit feature.
- I did not read `quality.rs`, `testing.rs`, `budget.rs` or the application crate in full (targeted greps only), nor any native/Docker behaviour.
- No repository evidence exists about real client support for the tasks extension; §8 marks that unknown rather than inferring it.

## 8) Answers to the specific questions

- **Is unconditional advertisement safe?** rmcp emits `extensions` only when `Some` (`capabilities.rs:230-231`), and `enable_tasks()` makes it `Some` with one key, so it is emitted on every negotiated version including `2024-11-05`. `strip_result_type_for_legacy_peer` does not touch it, and `CreateTaskResult` is not version-gated (only `InputRequiredResult` is, `handler/server.rs:246-259`). Safety against legacy clients is **not** demonstrable from this repository, and the ADR's justification that variation is impossible is wrong (F02): `initialize`/`discover` are overridable. Recommendation: keep the decision, correct the rationale, gate the flip on client evidence.
- **Is `auto → synchronous only if qualified short, else reject` right?** Yes — it is the literal D06 constraint (`m3-quality.md:46-54`) and it fails closed for Claude Code/Inspector today. **Which stock clients support tasks in 2026: unknown from repository evidence.** No file in `docs/` mentions the tasks extension or a client version supporting it; the recorded stock clients are MCP Inspector and Codex (M1 closure), with no capability record. Mark unknown and require G4 measurement.
- **Job permit vs request lease / orphan window.** No capacity is released before cleanup: the ADR correctly refuses to recycle the retained lease (matches `admission.rs:113-131` and ADR-030:48-50), and the job permit is released only after observed cleanup. The defect is the *trigger* for orphan cancellation (F01), not the accounting. The watchdog is compatible with the current-thread runtime only under the conditions in F09; it can signal but never preempt `run_joined`'s blocking closure.
- **Authority.** The masked fixed `-32602` with no data is consistent with `contract.rs` and `resources.rs` precedent and with SEP-2663. `JobOwner`'s "stdio-session principal" does **not** exist in code and must be introduced — and as defined it is process-constant and inconsistent with ADR-061's `owner_binding`, which omits it (F10).
- **Budgets.** Incoherent as tabulated: default and maximum sub-phase sums both overflow their parents, the sync row's "including cleanup" bound is contradicted by the cleanup row, and the 2 h TTL rationale does not survive counting cleanup (F03). Nothing contradicts L09/L10 directly — bootstrap 10 s, 1 MiB frames, 16 request slots and cancelled-response retention are all preserved verbatim.
- **Spike.** It does assert five-version advertisement, `-32021` with `requiredCapabilities`, poll-to-terminal with the flattened shape, cancel-ack-while-`working`, `ttlMs: null`, and a legacy `2024-11-05` peer receiving a task. It misses the not-declared × legacy matrix (F07) and carries a real 500 ms-TTL flakiness risk (F08). It adds no dependency and leaks no process. Keep it after M3-02 as an SDK-pin regression guard (see §7).
- **Restart/crash reconciliation.** New work, not existing behaviour (F06): today only a lazy, volume-only, fail-closed check exists in `RustGateway::new`.
