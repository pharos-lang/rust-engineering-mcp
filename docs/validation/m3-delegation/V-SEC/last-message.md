# V-SEC — Independent security / lifecycle / persistence review of the M3 delta

## 1. Verdict

**Revise.**

The containment core is sound and I could not break it. Specifically, and stated for the record because the orchestrator asked:

- **ADR-064's seccomp delta is exactly one rule.** `seccomp-rust-quality.json:1-153` is byte-identical to `seccomp-rust.json:1-153`; the appended rule (`:178-201`) is `socketpair(arg0 == 1 /*AF_UNIX*/, arg1 & 0x0f == 1 /*SOCK_STREAM*/, arg2 == 0)`, mirroring the existing `SOCK_SEQPACKET` rule's mask semantics and ignoring `SOCK_NONBLOCK|SOCK_CLOEXEC` exactly as the ADR says. `socket`, `bind`, `connect`, `listen`, `accept` remain absent. **No new phase silently needs more**: all five quality phases (`ListMutants`, `TestNextest`, `CoverageRun`, `CoverageReport`, `SemverCheck`, `MutationTest`) share this one profile (`rust_gateway.rs:54-66`) and differ only in argv; `verify_rust_generic` (`rust_applied.rs:291-299`) compares the applied profile against `phase.seccomp_profile_json()` as parsed JSON, so a phase silently getting a wider profile fails closed.
- **Network deny, non-root, read-only root and bounded tmpfs are enforced against the *applied* container**, not just requested: `rust_applied.rs:300-399` asserts `network_mode == "none"`, `readonly_rootfs`, `cap_drop == ["ALL"]`, `user == phase.user()`, exact `/work` and `/tmp` tmpfs option strings, `tmpfs.len() == 2 + extra`, `pids_limit`, `nano_cpus`, memory, and rejects `privileged`/`binds`/`devices`/`sysctls`/`ulimits`/`userns`.
- **The cargo-mutants mutated copy is a container-local tmpfs, not a named volume** (`rust_gateway.rs:610-617`, `/mutants-scratch`, `rw,exec,nosuid,nodev,size=256m,mode=0700,uid=65534`). It dies with the container, no exporter mounts it, `/source` is read-only for both mutation phases, `--no-config` blocks `.cargo/mutants.toml` output redirection, and all three exporters read `--directory=/mutants/mutants.out` with `--create` only. `lock.json` is excluded from the bundle (`--exclude=./lock.json`) and its bytes are consumed for the identity assertion and dropped (`mutation_test_gateway.rs:316-323`). Hostile project code cannot reach the host source, the report volume, another job's data, or a surviving process.
- **Cleanup dominates.** Every vertical joins/removes all owned containers before any volume (`rust_gateway.rs:1475-1527`), verifies label+nonce+image ownership before `rm`, re-checks absence after, and sets `quarantined` on any uncertainty; the gateway result is discarded if cleanup fails (`coverage_gateway.rs:344-361`, `mutation_test_gateway.rs:362-376`).
- **The JUnit reader is genuinely hostile-safe** (`nextest_junit.rs:197-201`): every `<!…>` construct is rejected before being read past, so DTD/ENTITY/CDATA expansion is never attempted; only the five predefined entities and non-recursive numeric refs decode.
- **The durable store's read path takes no lock, no lease touch and no TTL renewal** (`quality.rs:1258`), serves nothing beyond `size_bytes`, and masks every failure to `NotFound`.
- Every V00 finding I re-checked is fixed: `watchdog_record` no longer applies `work_deadline` in `Cleanup` (`job.rs:829-853`), `finalize` only converts a `Deadline` when `completion.is_none()` (`job.rs:1094-1104`), `can_transition_to` is now enforced (`:1105`), `run_joined_with(permit, …)` exists and is used (`workers.rs:348`, `coverage.rs:316`), `finish` measures serialized bytes against reservation and the 512 KiB bound (`job.rs:702-707`), and the watchdog accumulates errors instead of `?`.

What blocks acceptance is one **P1 availability defect reachable by a single well-formed `resources/read` or `tasks/get`** that freezes the whole session for the duration of a job — precisely the responsiveness ADR-060 promises — plus a partial-publication quota leak, an egress validator that is weaker than its own sibling, and a drift-detection gap that lands exactly on the two ADR-065 invariants the amendment leaves as the only ones that matter.

### On the ADR-065 amendment specifically

**I consider the amended shape contained.** The volume is a per-job local-driver tmpfs, labelled with the unpredictable process nonce, mounted only in coverage containers, absent from all three exporters, removed by `cleanup_coverage_with_target` with quarantine on uncertainty, and verified byte-for-byte (`rust_applied.rs:135-143` checks the exact option string including the absent `noexec`; `:544-573` checks name, mountpoint, driver, mode, propagation and rw polarity on both the applied and the requested mount).

**Yes, project-controlled content can end up executable there across phases — and it does not matter.** `CoverageRun` runs project build scripts and instrumented tests as uid 65534 with write+exec on that volume, so a hostile project can plant arbitrary executables in it. A `CoverageReport` phase runs `cargo` against a project-controlled `/source/.cargo/config.toml`, which could name a `rustc-wrapper`/`runner`/`linker` under `/work/coverage-target`. But that reachability already existed before the amendment: the volume was already mounted *exec* (read-only) in the report phases, and read-only mounts do not prevent execution. The amendment adds only **write** in a phase that could already execute what the run phase planted. It crosses no container boundary; everything so executed still runs uid 65534, `--network=none`, read-only rootfs, `cap_drop ALL`, `no-new-privileges`, ADR-064 seccomp, 128 pids, 1 CPU, 1 GiB — the same blast radius as the tests the job exists to run. Marginal delta: negligible.

**The verifier's assertions are *not* sufficient to detect drift** — see V-SEC-04. `verify_coverage` derives the expected rw polarity from the same `Phase::coverage_target_writable()` that builds the argv, and the ADR-065 matrix test builds its fixture from that function too. After the amendment the only remaining security-relevant invariants are (a) the keeper cannot write, and (b) the exporters have no mount at all — and neither is pinned by any literal assertion.

## 4. Contradictions with ADRs / AGENTS / security-model

1. **ADR-060:118-120 vs `resources.rs:312`** — "Resource reads remain on the worker permit in M3" and "only bounded in-memory `tasks/get`/`cancel`/`update` … remains responsive". Quality Resource reads are off the permit (an unrecorded decision, V-SEC-09) *and* can block the runtime harder than the permit ever would (V-SEC-01).
2. **ADR-061:85 ("eviction is rejected… reject-before-produce, never deleting promised live evidence") vs `quality_artifacts.rs:489-525`** — the durable path produces first and rejects afterwards, stranding committed evidence that consumes quota and is unreachable (V-SEC-02).
3. **ADR-061:128 ("member names are data… never extracts to host paths") vs `coverage_gateway.rs:44-57`** — the coverage bundle's `./`-rooting guarantee is not enforced against `prefix`-split names, while the mutation bundle's is (V-SEC-03).
4. **ADR-065:76 ("Runtime negative controls must prove … no non-coverage phase receives the target") vs `rust_applied.rs:1250-1280`** — the host-side assertion list omits the three coverage exporters, and the runtime controls for coverage have never executed (attempt7: coverage 0/8, remaining selections not executed).
5. **ADR-061:74 (bytes/artifact 32 MiB) vs `quality_artifacts.rs:29` (`MEMBER_CAP = 256 KiB`)** — a much smaller undocumented product limit whose exceed-behaviour is a hard failure, not the ADR's declared "reject before gateway; no descriptor".
6. **`SECURITY.md:311`** ("El … alcance de seguridad M1/M2 permanecen sin ampliación") vs ADR-065's new executable per-job volume — accurate for M1/M2 profiles, but the document never states the new M3 privilege (V-SEC-10).
7. **Not a contradiction, recorded deliberately:** ADR-063's `cargo-mutants` source build has `"sha256": null` in `sources.json:138` and records `crate_sha256`/`binary_sha256` after the builder emits them (`provision.py:105-112`). This is trust-on-first-provision, but the runtime gate is the immutable `APPROVED_RUST_IMAGE` digest, and the owner authorized this exact component set on 2026-09-05. Acceptable as recorded.

## 5. Missing security tests

Each of these would catch a real bug that today's suite cannot:

- **Registry-lock starvation (V-SEC-01):** hold the registry lock on a blocking thread (as a live job does), then issue `resources/read` on a `rust-quality-artifact://` URI and `tasks/get` on the async runtime; assert both return within a bounded time rather than blocking. No test in the tree exercises a quality Resource read concurrent with a running job.
- **Partial durable publication (V-SEC-02):** publish a job whose second member exceeds `MEMBER_CAP`; assert either that no descriptor survives, or that surviving descriptors are reachable through the returned locators. Also: an HTML bundle with 124+ entries, and one with exactly 128 vs 129 charged members.
- **USTAR `prefix` escape (V-SEC-03):** feed `validated_html_archive` a header with `name = "./x"` and `prefix = "../../etc"`, and one with typeflag `'0'` plus a non-empty linkname; assert rejection. The mutation validator has these; the coverage one does not.
- **ADR-065 polarity pinning (V-SEC-04):** literal per-phase expectations for `coverage_target_writable()`, including the three exporters, plus a negative case proving `verify_coverage` rejects a keeper container that was handed a writable target.
- **`source_unchanged` (V-SEC-05):** a test that can fail — mutate the captured bundle (or the host tree) between capture and the check and assert `false`. Today `mutation_runtime.rs:249,404,456` assert a constant.
- **Clock-hook reachability (V-SEC-06):** a `check-architecture.py` rule (or `compile_fail` test) asserting `with_clock_source`/`with_fault_injection` appear in no `src/` file.
- **M2 headroom coupling (V-SEC-07):** assert `M2_RECOVERY_HEADROOM_BYTES == RECOVERY_STAGING_HEADROOM_BYTES + RETAINED_METADATA_GROWTH_BYTES` rather than re-asserting the literal.
- **Coverage cancellation/timeout (recorded by W1, still unexecuted):** the coverage timeout and cancellation selections have never run — they sit behind attempt7's fail-fast stop. Cleanup-under-cancel with the new third volume is the case where the ordering bug would live.
