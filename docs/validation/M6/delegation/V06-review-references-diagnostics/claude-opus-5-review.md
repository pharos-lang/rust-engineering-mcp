# Review: `rust.analyzer.references` (M6-02) and `rust.analyzer.diagnostics` (M6-03)

## Verdict

**Block** — scoped to M6-03. One P1: the diagnostics path fails the *entire* call when a single diagnostic entry is refused by its domain constructor, and reports it as `unavailable / ANALYZER_CRASHED`. That is reachable from ordinary (not hostile) projects and misattributes the cause. M6-02 on its own would be *Approve with P2s*: the two-request set difference is sound in its core logic, the budget is genuinely shared, and position validation is correctly pre-session.

**Set-difference soundness, specifically** (asked in goal 1, no finding): ordering is irrelevant (`contains` scans the whole vector); duplicates degrade gracefully (a location present twice in the `true` answer and once in the `false` answer stays non-declaration for both copies); a location that is a declaration in file A and a use in file B is handled correctly because the difference is keyed on `(uri, range)`, not on file; external/sysroot locations are filtered downstream by `references_to_domain` after the difference, so an external declaration is dropped consistently from both the list and the count. The one asymmetry: a location present *only* in the `false` answer is silently discarded with no omission counter, since only `with_declaration` is published — that requires a non-monotonic peer and is P3-adjacent at worst. And a peer returning an empty `false` answer marks every location a declaration, which under `include_declaration: false` yields an empty visible list with `status: passed`, `completeness: complete` — disclosed only via `omitted_declarations`, which I consider adequate.

## What I verified

- **References budget sharing.** Both `remaining(budgets.query, query_started, Stage::Query)?` calls are evaluated against the same `query_started`, the second after the first request returns, so two requests can never exceed one query-phase budget. Failure on either is `?`-propagated and reaches `classify(error, Stage::Query)` / the `remaining` error, i.e. `TimeoutQuery` — no silent drop. Compared against the single-request path, which passes the *full* `budgets.query`; the new path is strictly more conservative.
- **Pre-session position validation.** `ProjectRegistry::analyzer_references` validates before `analyzer_finish` (and therefore before `port.analyze`) for every path: file-missing is already `FileNotInSnapshot` from `analyzer_prelude`; non-UTF-8 bytes make `LineIndex::new(...).ok()` `None`, `and_then` short-circuits to `false`, and the port reports `FileNotUtf8` as documented; otherwise `utf8_from_position(...).is_err()` decides. Tests cover line-beyond-EOF and column-beyond-EOL (col 31 on a 29-scalar line, implying col = len+1 is accepted, i.e. end-of-line cursor is valid). Multi-byte and empty-file cases are not tested; both follow from `LineIndex` semantics I could not inspect.
- **Information boundary (diagnostics).** Only `message`, `code`, `related[].message` and `file` carry peer-influenced content. `serverStatus`/stderr cannot cross: `schemas::Session` has numeric fields only (`stderr_bytes` is a count), and `wire_session` is unchanged. `ResponseError.message` is discarded — `matched.result.map_err(|error| server_error(error.code))` uses only the code. Every `error_message`/`summary` in both tools is `&'static str`. Two tests assert kill/reap text absence. The `message` bound *is* applied to the primary and to every `related` message; `code` is not (P2 above).
- **No `passed` without an answer.** `Passed` is constructible only inside the `AnalyzerOutcome::Answered` arm and only after the `AnalyzerResult` discriminant matches, otherwise `internal_error`. Failure arms always pass `None` for the list. `Incomplete` is set inside `data.completeness`, never as a status — the trim loop keeps `Passed` and appends `Reason::ResultLimit` idempotently.
- **Existing contract untouched.** No existing snapshot file is modified (only the two new ones are added; `git status` confirms no `M` on any `tests/snapshots/*.json`). `protocol.rs::bootstrap` retains indices 0–31 unchanged and appends 32/33, so the 32 frozen snapshots are still asserted byte-identical. `schemas.rs` changes are purely additive (`Reference`, `DiagnosticSeverity`, `RelatedInformation`, `AnalyzerDiagnostic`); no shared type used by the symbols schema was edited, so its `$defs` are unaffected. `release-smoke.py` appends both tools at the end of `TOOLS` and leaves all 32 existing `TOOL_SCHEMA_SHA256` entries untouched. Annotations are `readOnly: true / destructive: false / idempotent: true / openWorld: false` in both the Rust builders and both snapshots, matching the `TOOL_ANNOTATIONS` additions. `omitted`, `omitted_declarations` and `message_truncated` are all present and in `required`.
- **`analyzer_prelude`/`analyzer_finish` refactor is behaviour-preserving for symbols.** The sequence is identical (resolve → fingerprint → source → file presence → limits → single `port.analyze` → revalidate); the only reordering is `into_query()` now running before `ExecutionLimits::new_job`, both pure, both failing the same way. The fingerprint comparison moved from `&Option`/deref to an owned clone — same predicate. The new `PositionOutOfRange` arm in symbols' `output()` is a compile-forced, unreachable internal guard.
- **Status/code tables.** Both `*_failure_code` functions are exhaustive over `AnalyzerFailure`, every arm yields one `(code, status)` pair, `Cancelled` is rejected as a programming error before reaching them, and both tools' unit tests enumerate the full table. `RESULT_LIMIT` → `unavailable` with `data: null`, tested at `max_result = 16`.
- **Application-layer purity.** `crates/application/src/analyzer.rs` imports only `crate::` and `rust_engineering_domain::` items (`LineIndex`, `Position`, `ProjectIdentity` added); no `serde_json`, `rmcp`, or process APIs.

**Not verified (outside the diff):** `lsp_codec::{references_to_domain, diagnostics_to_domain}`, `record_omissions`, `remaining`, `convert`, `identifier`, `Question`'s fields, `LineIndex` semantics, the domain constructors' exact bounds (message/code/related count), `limits.frame_bytes`/`messages` values, and whether `diagnostics_to_domain` caps at `MAX_VISIBLE_RESULTS` (the schema declares `maxItems: 512`; the trim test uses 400). Also unverified: `docs/tools.md`, `docs/compatibility.md`, `docs/security-model.md` and the M6 matrix/delegation records were modified but are not in the diff, so I cannot confirm the documented input/output matches the two new snapshots. I ran nothing.
