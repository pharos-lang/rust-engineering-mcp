# Review: `rust_engineering_domain::analyzer` + `rust_engineering_execution::lsp_codec`

## Verdict

**Block** — one hostile-input crash (stack overflow, bypasses the domain's own depth invariant) and one protocol contract gap (missing `textDocument.codeAction` client capability, which can silently make the whole code-action feature non-functional against a spec-compliant server) are enough to block on their own. Several P2/P3 issues should be fixed or accepted knowingly before merge.

## Findings

| Sev | File:line / function | Finding | Evidence from the diff | 
|---|---|---|---|
| **P0** | `execution-adapter/src/lsp_codec.rs`, `walk_document_symbol` | Unbounded recursion once the 512-visible cap is hit: the `depth > 32` guard is only enforced inside the `if out.len() < MAX_VISIBLE_RESULTS` branch (via `domain::DocumentSymbol::new`'s check). Once the cap is reached, the function takes the `else { *truncated += 1; }` branch and then **unconditionally** recurses into `children` at the bottom of the function, with no depth check at all. A server response with ≥512 flat siblings followed by one very deeply nested chain (cheap to encode, well under the 1 MiB frame cap) drives native Rust recursion to an attacker-controlled depth, causing a stack overflow — an unrecoverable process abort, worse than the panics the workspace lints already forbid. As a secondary effect, `depth: u8` is incremented unconditionally (`depth + 1`) on every call with no bound in this path, so it will eventually wrap/overflow (panics in debug builds via overflow-checks, silently wraps in release) — moot only because the stack overflow happens first. | ```rust\nif out.len() < domain::MAX_VISIBLE_RESULTS {\n    out.push(domain::DocumentSymbol::new(... depth)?);\n} else {\n    *truncated += 1;\n}\nfor child in children.unwrap_or_default() {\n    walk_document_symbol(child, depth + 1, index, encoding, out, truncated)?;\n}\n``` |
| **P1** | `execution-adapter/src/lsp_codec.rs`, `client_capabilities()` | The fixed client capabilities never declare a `textDocument.codeAction` object at all (no `codeActionLiteralSupport.codeActionKind.valueSet`, no `isPreferredSupport`, no `dataSupport`, no `resolveSupport`). Per LSP 3.17, without `codeActionLiteralSupport` a spec-compliant server MAY respond to `textDocument/codeAction` with bare `Command` objects only. This codec's `resolve_action` unconditionally rejects any bare `Command` (`ActionRejection::Command`), so every code action could resolve to zero actions even when real quickfixes/refactors exist — exactly the "misspelled/missing key → rust-analyzer silently uses a different default" failure mode the milestone is designed to avoid. | ```rust\nfn client_capabilities() -> serde_json::Value {\n    serde_json::json!({\n        "general": {...}, "window": {...}, "workspace": {...},\n        "textDocument": {\n            "documentSymbol": {...},\n            "diagnostic": {},\n        },\n        "experimental": {...},\n    })\n}\n``` (no `codeAction` key anywhere) |
| **P2** | `execution-adapter/src/lsp_codec.rs`, `Decoder::try_take_frame` | `find(&self.buffer, ...)` re-scans the **entire buffered prefix** for `\r\n\r\n`/`\n\n` on every call to `try_take_frame`, which is invoked once per `feed()` and repeatedly while waiting for a body to complete. A peer that trickles a single ~1 MiB frame in small increments causes O(n²) byte comparisons (≈10¹² for a 1 MiB body fed 1 byte at a time) — a CPU-exhaustion vector bounded only by the query's wall-clock timeout, not by the codec itself. | ```rust\nlet crlf_pos = find(&self.buffer, b"\\r\\n\\r\\n");\nlet lf_pos = find(&self.buffer, b"\\n\\n");\n``` called at the top of every `try_take_frame`, with no cached header-offset/content-length state across partial-body feeds. |
| **P2** | `execution-adapter/src/lsp_codec.rs`, `resolve_action` | `ActionRejection::NotUtf8` is used as a catch-all whenever `indices.get(&file)` returns `None`, not only when bytes genuinely fail UTF-8 validation. Given M6 opens exactly one document per query (per the module's own doc comments), any `TextDocumentEdit` touching a second, legitimately in-scope `/source/*.rs` file (e.g. a multi-file rename) will hit this same path and be mislabeled `NotUtf8`, even though the file may be perfectly valid UTF-8 — it's simply not part of this session's index map. This corrupts the fidelity of the rejection-reason contract described in the task (every `WorkspaceEdit` rejection reason should mean what it says). | ```rust\nlet index = indices.get(&file).ok_or(domain::ActionRejection::NotUtf8)?;\n``` |
| **P2** | `execution-adapter/src/lsp_codec.rs`, `initialization_options()` | `"references": { "excludeImports": false, "excludeTests": false }` and `"lru": { "capacity": 64 }` could not be confirmed against the exact rust-analyzer 1.98.1 `generated_config.adoc`. In particular I'm not confident `references.excludeTests` is a real rust-analyzer key (I know of `references.excludeImports`); if it is misspelled/nonexistent, per this review's own framing that's a P1 (rust-analyzer ignores unknown config keys silently, so this would just be dropped with no fidelity signal). Flagging for verification rather than asserting a defect, since I cannot run rust-analyzer to check. | ```rust\n"lru": { "capacity": 64 },\n...\n"references": { "excludeImports": false, "excludeTests": false },\n``` |
| **P3** | `execution-adapter/src/lsp_codec.rs`, `parse_content_length` | `value.parse::<u64>()` accepts a leading `+` (Rust's integer `FromStr` permits an optional `+` sign), so `Content-Length: +10` is accepted where a canonical decimal-only header value should be rejected. Doesn't enable a bypass of any limit, but is a real gap against the stated "reject non-canonical Content-Length" hostile-peer goal, and there's no test for it. | `let parsed: u64 = value.parse().map_err(|_| CodecError::MalformedHeader)?;` |
| **P3** | `execution-adapter/src/lsp_codec.rs`, `parse_body` | Strict-parsing claim is incomplete: unrecognized top-level JSON-RPC keys are silently dropped (the function only ever inspects `jsonrpc`/`id`/`method`/`params`/`result`/`error`), and a message carrying **both** `method` and `result`/`error` is silently treated as a plain request/notification with the `result`/`error` fields discarded rather than rejected as malformed. | ```rust\nlet method = object.remove("method");\nlet has_id = object.contains_key("id");\nlet result = object.remove("result");\nlet error = object.remove("error");\nif let Some(method_value) = method { /* result/error dropped, no error raised */ }\n``` |
| **P3** | `domain/src/analyzer.rs`, `apply_edits`; `execution-adapter/src/lsp_codec.rs`, `resolve_action` | Both sort candidate edits with `sort_by_key(|(range, _)| range.start())` (start only, not `(start, end)`). For two edits sharing the same start (e.g. a zero-width insertion coincident with the start of a range replacement), the stable sort preserves input order, so acceptance vs. `OverlappingRanges` rejection — and the resulting text — depends on the order the edits were submitted, not on any canonical property of the ranges. No test exercises this. | `spans.sort_by_key(|(start, _, _)| *start);` / `file_edits.sort_by_key(|(range, _)| range.start());` |
| **P3** | `execution-adapter/src/lsp_codec.rs`, `code_actions_to_candidates` doc comment | The doc comment promises "one hostile or unsupported entry never fails the whole batch," but that only holds for the *resolution* step shown here. The `Vec<CodeActionOrCommand>` this function takes as input is (per standard serde `Vec<T>` semantics) deserialized all-or-nothing upstream (not shown in this diff); one array element that matches neither the `CodeAction` nor `Command` shape (e.g. missing required `title`) will fail that whole deserialization before this function is ever called, silently breaking the stated per-item isolation guarantee at a layer this diff doesn't show. | `/// Resolves every action in \`actions\` independently: one hostile or\n/// unsupported entry never fails the whole batch.` |
| **P3** | `execution-adapter/src/lsp_codec.rs`, `Decoder` | No explicit "poisoned" flag after a fatal `CodecError`: `self.buffer` isn't drained and `total_messages`/`total_bytes` are already mutated. Not attacker-exploitable on its own (relies on caller misuse), but worth a type-level guard (e.g. a `poisoned` bool returning a fixed error) given how much of the security model here rests on "session gets killed on fatal error." | `pub fn feed(&mut self, bytes: &[u8]) -> Result<Vec<RawMessage>, CodecError> { ... }` (no poison state) |

## What I verified

- **Position/byte/UTF-16/UTF-8 translation** (`LineIndex`): manually traced offset↔Position math for ASCII, BMP 2-byte, astral 4-byte/surrogate-pair, combining sequences, CRLF, BOM, empty file, trailing newline, offset==len, and out-of-range cases against the code; found the logic sound and consistent with the (extensive, well-targeted) existing tests. No panics, overflows, or silently-wrong positions found in this layer.
- **`apply_edits`**: traced sort/overlap-check/splice logic for correctness on non-overlapping, touching, and EOF-insertion cases; no slice/index panics possible given the established sort-then-check-then-splice invariant. Found the coincident-start tie-break issue noted above (P3).
- **Decoder framing**: traced CRLF-only enforcement, header line/byte caps, duplicate `Content-Length` rejection, mandatory `Content-Length`, message/byte counters, and confirmed no infinite loop is possible (buffer strictly shrinks by `needed ≥ 4` bytes each successful frame). Confirmed limits are checked before the per-frame `to_vec()` allocation. Found the leading-`+` and O(n²) rescanning issues noted above.
- **JSON-RPC message parsing**: confirmed batches, id-type (string/integer only, floats rejected), and result+error-both-present are all correctly rejected; confirmed a server-initiated request is never conflated with a response (dispatch is solely gated on presence of `method`), and this adapter only ever answers such requests with `-32601`, never a result (tested).
- **`Correlator`**: confirmed unknown/duplicate/late-response handling matches the stated semantics via direct code trace and the included tests; id reuse is not possible through the adapter's own `allocate()` (monotonic, session-scoped).
- **URI/path conversion**: traced `lsp_uri_to_file` against `file:///SOURCE`, `file://source/`, `..`, percent-encoded `..`, double slashes, and non-`.rs` — all correctly rejected as `External` at the code level (percent-decode happens before path validation, closing the encoding-bypass class of bug). Could not verify the underlying `validate_source_path` (not in this diff) for its exact `..`/empty-component rules.
- **WorkspaceEdit conversion**: confirmed `documentChanges` fully overrides `changes` (per spec), snippet (`insertTextFormat == 2`) detection, bare-`Command` vs. `CodeAction.command` disambiguation (via the untagged-enum type-mismatch mechanism), and resource-operation rejection are all correctly implemented and each has a positive test.
- **Fixed capabilities/options**: cross-checked every capability path named in the task against the emitted JSON one by one (see P1 above for the one confirmed gap; see P2 for two keys I could not independently confirm without the real rust-analyzer 1.98.1 schema).
- Confirmed no `.unwrap()`/`.expect()`/`panic!()`/`unsafe` appears anywhere in the diff (the `unwrap_or_default()` calls in `encode`/`config_digest` are safe no-op fallbacks for infallible serializations, not panics).
