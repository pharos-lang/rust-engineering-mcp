# Review: `rust.analyzer.symbols` (M6-01, tool 32)

## Verdict
**Block.** Two status/code-mapping defects contradict the documented contract (docs/tools.md) and the ADR-083 "one status+code" invariant this review was asked to check; one has no test coverage at all. Everything else is P2/P3 hardening and fidelity gaps, not blockers on its own, but should be fixed alongside.

## Findings

| Severity | File:function | Finding | Evidence | 
|---|---|---|---|
| P1 | `crates/mcp-server/src/stdio/analyzer.rs::AnalyzerTool::call` | `SANDBOX_DENIED` maps to **two different statuses** depending on code path. The normal path (`ExecutionError::Denied` via `operational()`) yields `unavailable`, matching docs. But when `bootstrap` (`!self.ready`) is true, the code computes that same `unavailable` outcome via `output(result, duration)?` and then **unconditionally overwrites** `value.outcome` with `Outcome::Blocked{ error_code: Code::SandboxDenied, ... }`. Same code, two statuses — violates "every variant maps to exactly one status+code" and directly contradicts `docs/tools.md`'s explicit statement that `SANDBOX_DENIED` is covered by `unavailable`. | `let mut value = output(result, duration)?; if bootstrap { ...; value.outcome = Outcome::Blocked{ error_code: Code::SandboxDenied, ... }; }` |
| P1 | `crates/mcp-server/src/stdio/analyzer.rs::encode_bounded` | The final over-budget fallback (after trimming symbols still leaves the encoded result over 512 KiB) returns `Outcome::Blocked{ error_code: Code::ResultLimit, ... }`, i.e. status `blocked`. `docs/tools.md` explicitly lists `RESULT_LIMIT` as *not* in the `blocked` bucket and groups it under "el resto" → `unavailable` ("`unavailable` cubre el resto ... límites de protocolo ..."). Code and published doc disagree on this code's status. | `docs/tools.md` (`blocked` cubre `CONFLICT, FILE_NOT_IN_SNAPSHOT, FILE_NOT_UTF8, UNSUPPORTED_PROJECT_CONFIG, PROJECT_NOT_FOUND, INVALID_PROJECT, OUTPUT_LIMIT_EXCEEDED`) vs `encode_bounded`'s `Outcome::Blocked{ error_code: Code::ResultLimit, ...}` |
| P2 | `crates/mcp-server/src/stdio/analyzer.rs::wire_limits` | `limits.total_timeout_seconds`/`initialize_timeout_seconds`/`query_timeout_seconds` in every response are always the fixed `domain::*_TIMEOUT_SECONDS` constants, never the caller's actual `request.timeout_seconds` (which *is* what's really enforced as the deadline via `ExecutionLimits::new_job(u64::from(request.timeout_seconds)...)` in `analyzer.rs` application crate). A caller passing `timeout_seconds: 30` who gets `TIMEOUT_TOTAL` will see `limits.total_timeout_seconds` claim the full ADR-084 ceiling (likely 180), not the 30s actually applied — misleading for debugging. | `fn wire_limits() -> schemas::Limits { ... total_timeout_seconds: domain::TOTAL_TIMEOUT_SECONDS as u32, ... }` vs app crate's `ExecutionLimits::new_job(u64::from(request.timeout_seconds).saturating_mul(1_000), MAX_RESULT_BYTES)` |
| P2 | `crates/mcp-server/src/stdio/analyzer/schemas.rs::DocumentSymbol/WorkspaceSymbol` | `name`, `detail`, `container` have `minLength` only — no `maxLength` and no character-class restriction, unlike `file` (`maxLength: 100`). Given the project's own threat model treats rust-analyzer as a potentially-compromised peer (`docs/security-model.md` new §M6), a hostile/buggy analyzer could return an LSP `documentSymbol`/`workspace/symbol` response with an oversized or control-character-laden `name` (LSP `name` is just a JSON string, not constrained to valid Rust identifier grammar); the only mitigation visible in this diff is the blunt whole-entry 512 KiB trim, not per-field sanitization. Domain-side validation (`NonEmptyText`, `DocumentSymbol::new`) is not in this diff, so I could not confirm a bound exists there. | `pub struct DocumentSymbol { ... #[schemars(length(min = 1))] pub name: String ... }`; security-model.md's own framing of rust-analyzer as adversarial |
| P2 | `crates/mcp-server/src/stdio/analyzer.rs::output` (CleanupUncertain arm) | Quarantine (`ExecutionError::CleanupUncertain`) and `InspectionError::Internal` both surface as a raw `ErrorData::internal_error(...)` (a JSON-RPC protocol error), not the tool's own `status: unavailable` structured envelope that the rest of the contract uses. The review's stated expectation is "quarantine → `unavailable`". Whether this is new-to-M6 or an established convention shared with M1–M5 tools could not be confirmed since those tool modules aren't in this diff. | `Err(...InspectionError::Execution(ExecutionError::CleanupUncertain))) => { return Err(ErrorData::internal_error("Gateway cleanup could not be verified...", None)); }` |
| P3 | `crates/execution-adapter/src/project_inspection.rs::AnalyzerPort::analyze` | `source_archive::encode(source)` + digest are computed **inside** the same `with_gateway` closure as `execute_analyzer`, extending the single-flight critical section with CPU-bound hashing unrelated to the LSP session; if this hashing step fails after a successful analyzer answer, the whole call is turned into an error, discarding a completed (possibly expensive, up to 180s) analysis. | `let result = self.with_gateway(control, |gateway| { let execution = gateway.execute_analyzer(...)?; let archive = super::source_archive::encode(source)...; let source_fingerprint = super::digest(&archive).parse()...; Ok(AnalyzerObservation{...}) });` |
| P3 | `crates/mcp-server/src/stdio/analyzer.rs::Input` | `expected_project_fingerprint`'s schema is `{"type": ["string","null"]}` with no `^sha256:[0-9a-f]{64}$` pattern, unlike the analogous output field. Server-side `FromStr`/`TryFrom` still enforces the format, but client-side schema validation can't catch a malformed value before the call. | `#[schemars(with = "Option<String>")] expected_project_fingerprint: Option<ProjectIdentityFingerprint>` vs. output's `#[schemars(regex(pattern = "^sha256:[0-9a-f]{64}$"))]` |
| P3 | `crates/mcp-server/src/stdio/analyzer.rs::encode_bounded` | The trim loop's threshold is `MAX_RESULT / 4` (128 KiB) rather than `MAX_RESULT` itself, with no comment justifying the 4x margin against `contract.encode()`'s envelope overhead (structuredContent + text content duplication, presumably). Functionally safe (a hard final check still enforces 512 KiB), but the margin is unexplained. | `while serde_json::to_vec(&value)...len() > MAX_RESULT / 4 { ... }` |

## What I verified
- **Snapshot/registration wiring**: `analyzer::NAME` is wired into all three required dispatch points in `stdio.rs` (`call_tool`, `get_tool` for `list_changed`-style lookup, and `list_tools`), appended last; no existing snapshot file is touched, satisfying "31 existing definitions byte-identical."
- **Tool count regression tests**: `catalog_status.rs`, `crate_inspect.rs`, `crate_search.rs`, `protocol.rs`, `test-release-smoke.py` all consistently bump 31→32; `protocol.rs`'s `assert_project_list` also checks the full ordered name list, so a missing registration or wrong position would fail these tests, not just a count check.
- **`Shadow`/`deny_unknown_fields` + `flatten` workaround**: on inspection this is the documented, correct serde workaround — the outer `Shadow` struct intentionally omits `deny_unknown_fields` (required, since `flatten` + outer `deny_unknown_fields` is a known-broken combination), but the flattened `Scope` enum carries its own `deny_unknown_fields`, and serde's flatten mechanism buffers the whole object, subtracts keys claimed by named sibling fields (`project_ref`, `expected_project_fingerprint`, `timeout_seconds`), and feeds the *residual* map to `Scope`'s deserializer — so a genuinely unknown top-level key (e.g. `"extra"`) does get rejected at the Rust level, not just via the JSON Schema's `unevaluatedProperties: false`. This is *not* the bug it initially looks like, contingent on the `jsonschema` crate correctly supporting 2020-12 `unevaluatedProperties` + `oneOf` (used only in the test's independent schema check, not verifiable from source).
- **Information boundary**: `wire_session()` never surfaces `kill_error`/`reap_error`; `Health`/`Readiness` are closed enums with no raw `message`; all `error_message` values in `analyzer.rs` are `&'static str` literals, never analyzer-derived text. A dedicated test (`no_stderr_or_kill_reap_text_ever_reaches_the_wire`) exercises this. No leak found.
- **Status invariants**: `Passed` is only constructed from `AnalyzerOutcome::Answered`; `Completeness` is data, never status; `Conflict`/`FileNotInSnapshot` always publish `data: None`. All confirmed by direct code reading.
- **Architecture boundary**: `crates/application/src/analyzer.rs` imports only `crate::*` and `rust_engineering_domain::*` — no `serde_json`, `rmcp`, or process APIs. No shared domain enum (`OperationalErrorCode`, etc.) is modified by this diff.
- **Tests can't pass with the mapping wrong for the paths they cover**: the failure-mapping table test (`every_analyzer_failure_maps_to_its_closed_code`) and the native/protocol tests would catch a wrong mapping for the cases they exercise — but there is **no test for the `bootstrap=true` path** (P1 finding above), so that regression would not be caught by this test suite.
- **`test-m6-runtime.py`'s tenth step**: correctly reuses the same `run_step` pass/fail discipline (`"test result: ok. 1 passed; 0 failed; 0 ignored;"` substring match) shared with the nine native cuts, so a filtered-out or compile-only run cannot report `pass`. No gap found here.
- **Docs vs. diff**: I could not independently verify `docs/validation/M6/01.md`'s 9/9 receipt or digest values since that file isn't part of this diff; nothing in the diff's new prose contradicts itself internally, aside from the RESULT_LIMIT/SANDBOX_DENIED status mismatches already flagged.
