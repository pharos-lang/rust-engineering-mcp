## Owner decision (A, 2026-09-12) — the postcondition

`rust.analyzer.action.apply` (W08, next package) will enforce **only** the structural `WorkspaceEdit` validation the codec already does (TextEdits in existing captured files, non-overlapping ranges, matching document version, bounded edits/bytes; Command/snippet/resource-op/external-URI rejected) plus the exact diff shown at preview and a plan bound to the analyzer/config/source identity. It does **not** run `cargo check` (unlike `rust.fmt.apply`/`rust.fix.apply`). An applied code action is therefore **not compile-verified** — that is a documented property, not a gap. Your job (W07) is the candidate-production side; keep that contract.

## Deliverables (domain + execution-adapter + application only)

### D1 — Domain (`crates/domain/src/{analyzer.rs,mutation.rs}`, additive)

- `MutationKind::AnalyzerActionApply` variant in `crates/domain/src/mutation.rs`. Check every exhaustive `match` on `MutationKind` across the workspace and handle the new arm; the journal (ADR-052) must still **reject** an unknown/incompatible kind before any effect (G6) — add/keep that.
- `AnalyzerAction` gains a stable identity input, but the hash itself is computed in the adapter (domain has no `sha2`, enforced by `scripts/check-architecture.py`). Provide in domain a **canonical, order-independent serialization** of an action for digesting: `AnalyzerAction::digest_input(&self) -> Vec<u8>` (or expose the normalized fields) covering `title`, `kind`, and the edits sorted by `(file, range.start, range.end)` with each `file`/`range`/`new_text` length-delimited so no two distinct actions collide. Unit-test that two actions differing only in edit order produce the same bytes and two genuinely different actions differ.
- `pub fn apply_action_to_bundle(before: &SourceBundle, edits: &[TextEdit]) -> Result<SourceBundle, AnalyzerError>`: group edits by file, apply each file's edits with the existing `apply_edits` (which already rejects overlaps and is order-independent), and return a new `SourceBundle` where each touched file is replaced by its edited bytes and untouched files are unchanged. Reject an edit whose file is absent from `before` (`FileNotInSnapshot`), an empty edit set (nothing to apply → a typed error the caller maps to "action produced no change"), and preserve `SourceBundle`'s invariants/limits (ADR-031). Tests: single-file multi-edit, two-file edit, empty edits, file-not-in-bundle, result exceeding a bundle limit.

### D2 — Execution-adapter (`crates/execution-adapter/src/analyzer_gateway.rs`, additive)

- `pub fn action_digest(action: &domain::AnalyzerAction, identity: &domain::AnalyzerIdentity, source_fingerprint: &domain::SourceFingerprint) -> domain::SourceFingerprint`: sha256 (use the crate's existing `digest()`/`Sha256`) over `action.digest_input()` ++ `identity.version` ++ `identity.binary_sha256` ++ `identity.config_digest` ++ `source_fingerprint`, parsed back into `SourceFingerprint`. Every resolved applicable action in a `CodeActions` answer carries this digest — extend `AnalyzerResult::CodeActions`/the candidate so the digest is available to callers (either add `digest` to `AnalyzerAction`/a wrapper, or return a parallel structure). Whatever shape you choose, `rust.analyzer.actions` (W08) must be able to publish, per applicable action, `{action_digest, title, kind, is_preferred, applicability, edits_summary{files, edits, bytes_delta}}`, and the apply-preview must be able to find an action **by digest**.
- A gateway entry point for apply-preview, e.g. `RustGateway::resolve_action_candidate(source, file, range, action_digest, identity_expectations, limits, cancel) -> Result<ActionApplyResolution, ExecutionError>`, that: runs a single CodeActions session on the captured `source` (reusing the existing lifecycle and the `AnalyzerQuery::CodeActions` path), computes each applicable action's `action_digest`, finds the one equal to the requested `action_digest`, and returns its resolved `AnalyzerAction` + the live `AnalyzerIdentity` + `source_fingerprint` + the LSP session execution fingerprint. If no applicable action matches the digest → a typed `ActionStale` (the action the caller previewed is gone or changed under a new capture); if the matched action's edits fail structural validation (they were resolved through the codec, so this is belt-and-braces) → the corresponding `ActionRejection`.
- Do **not** apply the edits or build the candidate in the gateway; return the resolved action + identities to the application layer.
- Native cut(s) in `crates/execution-adapter/src/analyzer_native.rs` (`#[ignore]`, receipt machinery like the others): `m6-11-code-actions` on a fixture where the real rust-analyzer offers at least one **applicable** code action under the M6 minimal config (assists like "add explicit type", "generate …", or a quickfix; you do NOT know which are available under our config, so **record every applicable action's title/kind/edits in the receipt and assert loosely**: at least one `Applicable` action whose edits are non-empty and apply cleanly via `apply_action_to_bundle` to produce an `after` that differs from `before`; and, if the fixture can elicit one, that a `Command`/snippet/resource-op action is `Rejected` with the right reason — if none appears, record that and do not fail). **Do not hard-assert a specific action title**; the orchestrator will confirm the actually-available actions on the calibration run and tighten. If NO applicable action appears at all on your chosen fixture, stop and report with what the real binary returned so the orchestrator can pick a better fixture (mirror of the references/diagnostics lessons).

### D3 — Application (`crates/application/src/analyzer.rs`, additive)

- `AnalyzerPort` extension for actions: `resolve_actions(source, file, range, only, control) -> Result<ActionsAnswer, InspectionError>` (the list, each with digest) and `resolve_action_candidate(source, file, range, action_digest, control) -> Result<ResolvedActionApply, ...>` (the matched action + identities), delegating to D2.
- `ProjectRegistry::analyzer_actions(reference, ActionsRequest, port, control)` reusing the shared `analyzer_prelude` capture/fingerprint/file-in-snapshot helper (do not change the symbols/references/diagnostics behaviour): returns the actions list with per-action `action_digest`, applicability, edits summary, plus the standard envelope facts.
- `ProjectRegistry::analyzer_action_candidate(reference, ActionPreviewRequest{file, range, action_digest, expected_project_fingerprint}, port, control) -> Result<AnalyzerActionCandidate, AnalyzerRequestError>`: revalidate project; check `expected_project_fingerprint` (mismatch → `Conflict`); capture a **fresh** SourceBundle; resolve the action by digest (D2); if `ActionStale` → typed error; apply the edits to the captured bundle via `apply_action_to_bundle` to produce `after`; build a `MutationCandidate { kind: MutationKind::AnalyzerActionApply, before: <the touched files' bundle>, after, validation: <the m6-analyzer-action-v1 string> }` exactly the way `rust.fmt.apply` builds and encodes its candidate (mirror `stdio/mutation.rs`'s validation encoding: version `m6-analyzer-action-v1`, `mode=local_coordinated`, platform, image_id, configuration_fingerprint, execution_fingerprint (the analyzer LSP session's), rust_version, cargo_version, candidate_source_fingerprint, then a tail carrying the analyzer `version`, `binary_sha256`, `config_digest`, and the `action_digest`). Return the candidate + workspace_root so W08 can hand it to `MutationPlans`/the writer. **The application layer must not import `serde_json`/`rmcp`/process APIs** (architecture gate). Unit tests with a fake port: happy path (candidate produced, after ≠ before), fingerprint conflict, action-stale, file-not-in-snapshot, an action whose edits don't apply.
