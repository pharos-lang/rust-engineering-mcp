# Independent re-review of the M5 profiling containment corrections (gate G8)

Reviewer: Claude Opus 5, read-only, high effort. Date: 2026-09-09.
Branch `ai/m5-performance`, commit `875c8902e737b28cc432ebe5f886de0bd41b0503`.

## Verdict

**Pass.** The P1 is genuinely closed, and closed three times over rather than once. A hostile profiled binary now has no path to a published measurement: `emit` opens *both* artifacts `O_EXCL` and returns success only if *both* creations succeed, so pre-creating either one turns the run into exit 4, which the gateway does not export at all; the helper empties its PID namespace before it renders or writes anything, and it checks `getpid() == 1` instead of assuming it, degrading to a narrow kill and an honest `namespace_drained: false` when the assumption does not hold; and the host refuses any manifest whose key set is not exactly the nineteen keys, whose schema is not the one string, whose three argv parameters are not the ones this host itself put on the command line, whose `namespace_drained` is not `true`, or whose two derivable counters do not equal what the host's own parser found in the stacks. I worked the attack from the child's side — pre-create one artifact, pre-create both, symlink, hard-link, directory, unlink-and-hold-fd, double-fork, plant during `ProfileBuild`, kill the helper mid-run — and every path lands on a refusal, not on a publication. The test-only denial switch is what it claims to be: `const fn ... -> false` outside `cfg(test)`, a thread-local under it, reaching exactly one expression (`seccomp_profile_name`/`seccomp_profile_json` for `ProfileRun`), leaving the phase list, the entrypoint, the argv and the `verify_applied` comparison untouched, and the denial it produces is the guest kernel returning EPERM under the committed quality profile — a real refusal, driven through `performance_port::profile` and `validate_profile_observation`, now recorded as `denial-control` in the generated receipt with helper exit 3 and `perf_errno = 1`. The image digest supersession is clean, and I verified it rather than believed it: re-running `fixtures/rust-runtime/m5/provision.py` on this tree reproduces the build context digest `471f90954dab0f6d…` byte for byte against `M5-provisioning.json`, so the admitted image `e0a5ca16…` was built from exactly the helper sources now on disk, and the admission list holds exactly one M5 digest. What is left is one carried-forward P2 (`verify_applied`, knowingly deferred, still defensible) and a P2 of evidence: the entire fix lives in `fixtures/profile-helper/src/linux.rs`, which has zero tests, is compiled by no gate on the development platform, and is exercised by no selection that forks — `descendants_reaped` is `0` in every receipt on the tree, so the drain has never been observed reaping anything. Neither publishes unauthenticated bytes, so neither blocks.

## Findings

### P2 — the correction's load-bearing code is untested, uncompiled by any gate, and unobserved by any receipt

**Files**
- `/Users/cburgosro/Projects/rust-mcp/fixtures/profile-helper/src/linux.rs:520-568` (`drain_namespace`), `:475-503` (`kill_namespace`, `wait_any`), `:331-354` (`emit`, `create_new`) — 0 occurrences of `#[test]` in the whole file
- `/Users/cburgosro/Projects/rust-mcp/fixtures/profile-helper/src/main.rs:15-16` — `#[cfg(target_os = "linux")] mod linux;`
- `/Users/cburgosro/Projects/rust-mcp/scripts/gate.py:171-172` — the only two gate steps that touch the helper are `cargo fmt --check` and `cargo test` on the **host**, which is macOS ARM64
- `/Users/cburgosro/Projects/rust-mcp/docs/validation/M5-03-runtime.json` — `profile-cpus-sampled` records `descendants_reaped: 0`; `denial-control` records `descendants_reaped: 0`

**What is wrong.** `linux.rs` is a module of the *binary* crate gated on `target_os = "linux"`. On the platform where every gate runs, it is not compiled, not linted and not tested. I confirmed this directly: `cargo test --manifest-path fixtures/profile-helper/Cargo.toml` runs 57 tests, all of them from `lib.rs`; the `src/main.rs` test binary runs 0. The only thing that ever compiles the drain is the guest image build inside the container, which happens when someone reprovisions. So a change to `drain_namespace`, `kill_namespace`, `wait_any` or `create_new` can land, pass `m5-helper-fmt`, `m5-helper-tests`, `cargo check`, `clippy` and every native cut, and be discovered only at the next `build-m5-runtime.py` — or not at all, if it compiles and is merely wrong.

Separately, no qualification selection forks. `fixtures/profile-workload` is a straight-line workload (`main → level_one → level_two → known_hot_frame`), so in every recorded run the child is reaped by `try_reap` before `drain_namespace` is even called, `kill(-1)` signals nothing, and `wait_any` returns `ECHILD` on its first pass. `descendants_reaped: 0` in all five selections is therefore not evidence that the drain reaps descendants; it is evidence that there were none.

**Why it matters.** Trace the residual chain. If `drain_namespace` ever returned `namespace_drained: true` while a process was still alive, the P1 reopens in full: a surviving grandchild can rewrite both artifacts after `emit` created them (`O_EXCL` protects creation, not the content of a file that already exists), and it can forge a pair that passes every host check — the schema is a public constant, the nineteen keys are fixed, the three echoed parameters are the ones on the argv it can read from `/proc/1/cmdline`, `namespace_drained: true` is a literal, and `stacks_written`/`samples_collected` are trivially made to agree with a stacks file the same process writes. Every other barrier is upstream of that one. So the drain's correctness is the last line, and the only thing standing behind it today is reasoning — mine and the author's.

I read that reasoning carefully and it holds: `kill(-1, SIGKILL)` from the namespace init reaches every task in the namespace except pid 1 and the caller's own thread group; every process in a PID namespace is reparented to its init, so `waitpid(-1, WNOHANG) == ECHILD` is equivalent to "the namespace holds only me"; a process the caller cannot signal stays a child, yields `Waited::Pending`, and times out into `namespace_drained: false`; the sweep is re-issued each poll so a fork racing its own death is caught; and `DrainPlan::DirectChildOnly` never claims `namespace_drained`. I found no defect. But "the reviewer found no defect by reading" is a weaker artifact than G5 asks for on a control this load-bearing.

**What would fix it.** Cheapest first: (1) add a `rust-mcp-profile-fork` bin target to `fixtures/profile-workload` that double-forks a grandchild which busy-loops appending to `/profile/stacks.txt`, and a selection asserting `descendants_reaped > 0`, `namespace_drained == true`, and that the published counters still reconcile — that single selection exercises the drain, the re-sweep and the reconciliation at once; (2) add a second selection whose grandchild pre-creates `/profile/manifest.json`, asserting helper exit 4 and `SecurityError::InvalidMetadata`; (3) add `cargo clippy --manifest-path fixtures/profile-helper/Cargo.toml --target aarch64-unknown-linux-gnu` to `gate.py` so the syscall path is at least type-checked and linted by a gate rather than only by the image build.

**Does not block:** I found no defect in the code this finding says is unverified, and the failure mode requires a defect. It is an evidence gap, not an open door.

## What I verified, and found sound

**Q1 — the drain, and whether pid 1 is checked rather than assumed.** Checked, at `linux.rs:521` via `drain_plan(self_pid())` (`lib.rs:1229-1235`), a pure `const fn` on the observed pid and nothing else, with tests at `lib.rs:2588-2600`. Off pid 1 the plan narrows to the known child and `namespace_drained` is `false` by construction (`linux.rs:541` makes the claim conditional on `plan == WholeNamespace`, so even an immediate `ECHILD` under the narrow plan does not claim a drained namespace). `kill(-1, SIGKILL)` is called only after that answer (`:522-523`), and the safety comment at `:475-485` states the invariant the call site establishes.

**Can a descendant survive any path?** I traced all of them. All three loop exits — sample limit (`:206-209`), child exited (`:210-216`), duration elapsed (`:217-220`) — fall through to the same `:228-241` sequence: disable the events, kill and blocking-reap the direct child if it has not already been reaped, then `drain_namespace(Some(child))`, and only then `drain_all`, `render()` and `emit`. The `abandon` path (`:271-293`) drains on the same rule even though the child was never `SIGCONT`ed and no project code ran. The "child never started" path (`:153-166`) calls `drain_namespace(None)`, which under `WholeNamespace` still sweeps and reaps, so a fork that happened before the failure is not left behind. That closes the pre-existing G3 gap the disposition claims it closes. The kernel semantics hold up: `kill(-1)` from the namespace init reaches every task in the namespace but not pid 1 or the caller's own thread group; every process in the namespace is reparented to pid 1 on its parent's exit, so `waitpid(-1, WNOHANG) == ECHILD` really does mean "empty"; a task in uninterruptible sleep, or one the caller cannot signal, stays `Waited::Pending` and hits `NAMESPACE_DRAIN_TIMEOUT` (5 s) into `namespace_drained: false`; `Waited::Failed` also yields `false`; the sweep is re-issued every poll (`:552-558`) so a process forked between a sweep and its delivery is caught on the next one, bounded by the container's own `--pids-limit=128`. A nested PID namespace would require `CLONE_NEWPID`, which the container's dropped capabilities and `no-new-privileges` put out of reach, and even then the nested init is a descendant and the kernel tears the nested namespace down with it. And because pid 1 exiting destroys the namespace, the window the drain protects is exactly the one that matters: between the child's death and the two writes.

**Is a failed drain fatal?** Not in the helper — it emits `EXIT_SUCCESS` with `namespace_drained: false`, which I initially read as a degraded success. It is fatal at the host, on every reachable path: `manifest_describes_this_run` (`performance_port.rs:613-614`) requires `namespace_drained && descendants_reaped <= APPLIED_PIDS`, and it runs for every `output.run.is_some()`, which is every case where a helper ran at all. The denial path goes through the same check. The build-failed path constructs `HelperManifest::default()` host-side (`:714`) and never reads guest bytes. Tests at `:1496-1506` drive both the `false` refusal and the pid-limit bound, including the boundary (`128` accepted, `129` refused). The single-point-of-enforcement is worth knowing about — the artifacts themselves carry no signature — but `parse_helper_manifest` is the only production consumer of `output.manifest` in the whole crate, and I checked.

**Q2 — `O_EXCL` on every path.** `emit` (`linux.rs:331-343`) is the sole writer, reached from exactly three call sites (`:165`, `:265`, `:292`), and `create_new` (`:347-354`) uses `OpenOptions::create_new(true)`, i.e. `O_WRONLY|O_CREAT|O_EXCL`, which refuses a pre-existing file, a symlink and a directory alike. Crucially, `emit` returns the caller's code **only if both** writes succeeded, so pre-creating either artifact alone is enough to force exit 4 — the partial-forgery cases (plant the manifest, let the helper write the stacks, or the reverse) do not produce an exportable run. Exit 4 is honest: the doc comment at `:325-330` states the reasoning, and the constants (`lib.rs:19-25`: 0 success, 2 invalid argv, 3 profiler unavailable, 4 internal failure) keep a write refusal from ever masquerading as `profiler_unavailable`. The panic path in `main.rs:26` returns 4 without writing anything and without draining, which is also correct: pid 1 exiting destroys the namespace, and 4 is not exported.

**Q3 — can a hostile child still get a manifest accepted?** No. I worked it from the child's side and every branch terminates in a refusal. Pre-create one or both artifacts → exit 4 → `exported` is `None` (`performance_gateway.rs:2349-2353`) → empty manifest → `serde_json::from_slice` fails → `InvalidMetadata`. Survive the drain and overwrite → requires `namespace_drained: false`, refused. Plant during the build → `ProfileBuild` does not mount the output volume (`:513-516`, `output: false` inherited from `all`), and `/work/target` is read-only during `ProfileRun` (`:543`). Add a third file to `/profile` → the exporter passes `--no-recursion` with exactly two literal names (`:388-396`) and `decode_profile_tar` (`:1432-1471`) refuses any other member name, any duplicate, any non-regular type. Kill the helper → the container's exit code is the helper's, and pid 1 of a namespace discards default-action signals from inside it; any exit outside {0, 3} skips the export entirely.

**Is the key-set check plus `deny_unknown_fields` sufficient given an absent `Option` reads as `None`?** Yes, and the belt-and-braces is not redundant in the way it first looks. `parse_helper_manifest` (`:576-592`) deserializes twice: once into a `serde_json::Map` to assert `len() == 19` *and* that all nineteen expected keys are present — which together mean exactly those nineteen — and once into the struct. The `len()` half is what catches the three `Option<i32>` fields, which `deny_unknown_fields` alone would have let default silently; the `deny_unknown_fields` half keeps the constant list and the struct from drifting. Duplicate keys cannot inflate `len()` (the map collapses them) and cannot slip through the typed parse either, since serde's derive rejects a repeated field. `null` for a required scalar, a string where a number belongs, a negative for a `u64` — all deserialization errors. The tests at `:1418-1451` remove each of the nineteen keys in turn, append an unknown one, and drive four wrong schemas including the one the old smoke record misspells, plus `b""` and `b"{}"` — the two documents the previous reader turned into a clean set of zeros.

The reconciliation itself is real, not decorative. `manifest_describes_this_run` (`:599-629`) re-derives all three echoed parameters from the same expressions the gateway put on the argv (`frequency_hz`, `duration_ms().min(PROFILE_MAX_SAMPLING_MS)`, `PROFILE_MAX_DEPTH` — compare `performance_gateway.rs:430-441`), so it is a genuine equality against host state and not a self-check. `manifest_matches_the_artifact` (`:639-642`) is exact rather than approximate, because `parse_folded` refuses unsorted input (`FoldedError::NotSorted`) and therefore merges only adjacent repetitions, making `distinct_stacks` precisely the key count of the helper's own `BTreeMap`. The `None` arm at `:745-749` is the part I most expected to be soft and is not: a sampler that ran, was not denied, and wrote a stacks file the host cannot parse is refused outright rather than published beside an empty artifact. Tests at `:1453-1522` drive both counters wrong in both directions, all three parameters wrong, `cpus_sampled: 0` with samples, an errno on an undenied run, and an unparseable artifact. `helper_status` (`:644-653`) maps anything it does not recognise to `ProfilerUnavailable` rather than to a success, and the denial-coherence clause then requires an errno and three zeros, so an unrecognised status on a run that actually sampled is a refusal, not a silent downgrade.

**Q4 — the test-only denial switch.** It cannot affect a shipped binary. `#[cfg(not(test))] const fn perf_event_open_denied() -> bool { false }` (`performance_gateway.rs:148-151`) is what every non-test compilation of the crate sees, including the crate as a dependency of `rust-engineering-mcp`, integration tests and doctests; `cfg(test)` is set only when compiling *this* crate's own unit-test harness. There is no feature flag, no env var and no build-script path that flips it — I checked. `profiling_profile()` reduces to `self == Self::ProfileRun` and folds away. It cannot perturb a concurrent test: the switch is a `thread_local!` `Cell`, the gateway builds argv, computes fingerprints and runs `verify_applied` on the calling thread, and thread-locals are not inherited by anything. And the denial it produces is the product's own refusal path: the switch reaches exactly two expressions (`seccomp_profile_name`, `seccomp_profile_json`, both at `:550-568`) and nothing else — the entrypoint stays `/opt/perf/bin/rust-mcp-profile-helper`, the argv is unchanged, the phase list is unchanged, `verify_applied` still runs and still compares the applied seccomp JSON against the phase's declared one, and the committed quality profile's `defaultAction: SCMP_ACT_ERRNO` with `defaultErrnoRet: 1` is what makes `perf_event_open` return EPERM inside the guest. `the_denial_switch_moves_only_the_sampling_phase_to_the_quality_profile` (`:2985-3011`) pins all of that. This is the finding I was told to be most suspicious of, and I could not make it into a weakening: it does not disable a check, it selects between two committed policy files, and it selects the *more* restrictive one.

**Q5 — widening the export to helper exit 3.** It widens nothing a hostile child can reach. Exit 3 is produced at exactly one place, `abandon` (`linux.rs:292`), which is called only from `:170` and `:183` — both before `SIGCONT`, while the child is still stopped in `pre_exec` and has not yet reached `exec`. On that path the project's binary has never executed a single instruction, and the two artifacts are unambiguously the helper's. Exit 3 cannot arrive any other way: `EXIT_PROFILER_UNAVAILABLE` appears nowhere else, an argv error is 2, and the child's own exit code travels in the manifest rather than becoming the container's. The change is also necessary rather than cosmetic — the errno lives only in the manifest, so exporting only exit 0 made ADR-074 §3's denial unreportable by construction, which is exactly what the code comment at `:2344-2348` says.

**Q6 — the digest and the receipts.** The admission list holds exactly one M5 digest: `APPROVED_M5_IMAGE` = `performance_port::M5_IMAGE` = `sha256:e0a5ca16…`, appearing once each in `rust_gateway.rs:922-926`, `host_config.rs:151-158` and `performance_port.rs:56-57`, with `admitted()` (`:98-104`) refusing every other image before a container exists and a native selection proving it. ADR-077's amendment is candid: it says supersedes-not-accompanies, states why admitting both would be wrong, and records that only the helper changed (`70fa813d…` → `18eaac41…`) while `cargo-bloat` came out byte-identical. I did not take that on trust. Re-running `fixtures/rust-runtime/m5/provision.py` against this working tree reproduces `context_sha256s_digest = 471f90954dab0f6dca857c94c1694c67c4f9b712ce000879566b1a90bd411275`, identical to both `sha256sums_sha256` and `prepare.context_sha256s_digest` in `M5-provisioning.json`, over 46 files and 10,796,061 bytes; the context's `helper/src/lib.rs` and `helper/src/linux.rs` diff clean against `fixtures/profile-helper/src/`.
