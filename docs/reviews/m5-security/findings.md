## Verdict

The containment story for M5 profiling is, in its sandbox dimension, real and unusually well evidenced: the seccomp delta is byte-for-byte one syscall in one phase, the capability is a positive host grant checked twice before any container exists, the applied-configuration check catches a `CAP_PERFMON` injection and a wrong profile, the SVG cannot carry active content by construction rather than by test selection, and cleanup is joined and quarantining on every exit path including the error paths. What does **not** hold is the claim underneath all of it — that the numbers and stacks the tool publishes are the *product's* measurement. The profiled binary (hostile by definition) runs as the same uid, in the same container, with `/profile` mounted **read-write**, and the helper's two artifacts are ordinary files in that directory written after the child is killed but before the container is torn down, while any grandchild the child forked is still alive. Nothing on the host reconciles the manifest against the stacks, and the manifest's `schema` key is never even checked. Separately, the M5 gateway reimplements the applied-configuration check as a strict subset of the `rust_applied` matrix every other gateway (M4 included) uses — dropping `Sysctls`, `Devices`, `PidMode`, `UsernsMode`, `MaskedPaths` and a dozen more — on precisely the phase that runs project code with an extra syscall allowed. Finally, the mandatory permission-denied oracle for M5-03 exists only in a hand-written receipt whose numbers do not match any reproducible run. M5 should not close on the profiling axis until those are resolved; the M5-01 blocker itself is handled correctly and the refusal to widen `SourceBundle` is the right call.

## Findings

### P1 — The profiled child can overwrite the profiler's own artifacts, and the host accepts them unreconciled

**Files**
- `/Users/cburgosro/Projects/rust-mcp/crates/execution-adapter/src/performance_gateway.rs:468-472` (`ProfileRun` mounts `output`), `:485-495` (`output: matches!(self, Self::BenchRun | Self::ProfileRun)` → `/profile` is **writable** in the phase that executes project code), `:56`, `:392-397` (`/profile/stacks.txt`, `/profile/manifest.json` passed on argv)
- `/Users/cburgosro/Projects/rust-mcp/crates/execution-adapter/src/mutation_gateway.rs:13-14` — `VOLUME_OPTIONS = "…uid=65534,gid=65534,mode=0700…"`; the container user is `65534:65534` (`performance_gateway.rs:729`), so the child owns and can write that directory
- `/Users/cburgosro/Projects/rust-mcp/fixtures/profile-helper/src/linux.rs:204-206` — only the **direct** child is `SIGKILL`ed; the helper is PID 1 (`--init=false`) and never reaps or kills descendants, so a double-forked grandchild survives
- `/Users/cburgosro/Projects/rust-mcp/fixtures/profile-helper/src/linux.rs:289-302` — `emit()` writes both artifacts with plain `fs::write` after the child is dead, then returns; the container is torn down only when PID 1 exits
- `/Users/cburgosro/Projects/rust-mcp/crates/execution-adapter/src/performance_port.rs:417-443` (`HelperManifest`: no `schema` field, no `deny_unknown_fields`, every field `#[serde(default)]`), `:504` (`unwrap_or_default()`)

**What is wrong.** A hostile project's binary double-forks a grandchild that busy-loops rewriting `/profile/stacks.txt` and `/profile/manifest.json`. The helper kills only the direct child, so the grandchild is alive across `drain_all`, `render()` and both `fs::write` calls, and the last write before PID-1 exit wins. The export phase then tars whatever is on disk, and `profile_observation` maps a fabricated manifest straight into `ProfileCounters`, `ProfileStatus` and `ProfileCompleteness`. `observation.consistent()` and `validate_profile_observation` cannot catch it: `profile_completeness` is *derived from* the same fabricated counters, and `options`, `backend`, `vendor_fingerprint` and `execution_fingerprint` are all supplied by the product, not the manifest. A simpler, deterministic denial variant needs no race at all: the child pre-creates `stacks.txt` mode `0444` (a non-root owner cannot reopen their own `0444` file for writing), `emit()` fails, and the run becomes `ProfilerUnavailable` without an errno → `InvalidMetadata`.

**Why it matters.** ADR-074 §5 ("se declaran siempre `samples_collected`, `samples_lost`… no se rellena"), `SECURITY.md:398-406`, and `docs/validation/M5-03-profiling-native.json` all present these counters as the helper's observation. `docs/security-model.md:691-695` declares the unauthenticated-origin residual risk **only for benchmarks** ("las muestras las produce el harness del proyecto"); the profiling rows claim the opposite — that the product owns the measurement because it owns the helper. The plan's threat delta names "artifact spoofing" and "benchmark que falsifica output" as things M5 must address. Here neither is addressed nor declared.

**What would fix it.** In order of value:
1. Make the namespace empty before emitting. The helper is PID 1 in its own PID namespace: `kill(-1, SIGKILL)` then reap until `ECHILD`, *then* `emit()`. That is a complete and cheap fix for the race, and it also closes the G3 gap that the helper's `duration_limit` path leaves descendants running.
2. Reconcile host-side. Require `manifest.schema == "rust-engineering-mcp.profile-helper.v1"`, and check `manifest.stacks_written == folded.distinct_stacks` and `manifest.samples_collected == Σ counts` against the parsed artifact; refuse on mismatch. This also catches a merely *buggy* helper, not just a hostile child.
3. If neither is taken, the honest minimum is to add a profiling row to `docs/security-model.md`'s threat table with the same candour as the benchmark row, and to soften ADR-074 §5 and `SECURITY.md` accordingly.

### P2 — The M5 gateway's applied-configuration check is a strict subset of the qualified one

**File** `/Users/cburgosro/Projects/rust-mcp/crates/execution-adapter/src/performance_gateway.rs:893-1001` (`AppliedHostConfig`, `verify_applied`).

Every other gateway verifies the daemon's answer through `rust_applied` — `security_gateway.rs:536`, `mutation_gateway.rs:357`, `rust_gateway.rs:1755/1808/1852/1901/1965/2025/2075/2124`, `resolution_gateway.rs:258`. `rust_applied::no_host_authority` (`rust_applied.rs:104-155`) and `applied_limits_ok` (`:156-195`) additionally reject `AutoRemove`, `GroupAdd`, `UTSMode`, `OomKillDisable`, `OomScoreAdj`, `DeviceCgroupRules`, `StorageOpt`, `Annotations`, `Init`, `UsernsMode`, `CgroupParent`, **`Sysctls`**, `Ulimits`, the fixed `MaskedPaths`/`ReadonlyPaths`, `PidMode`, `VolumesFrom`, **`Devices`**, `DeviceRequests`, `PublishAllPorts`, `PortBindings`, `RestartPolicy`, `LogConfig`, `Config.Volumes`, `AttachStdin`/`StdinOnce`. `performance_gateway::verify_applied` checks none of them.

The module comment at `:920-930` explains the duplication ("its helpers are private to that module and it has no M5 phase type") but does not acknowledge that the result is weaker. ADR-074 §3 says "El perfil aplicado se verifica contra el declarado por fase, **igual que ADR-064**", and `M5-03-profiling-native.json`'s `containment` block asserts `sysctl_changed: false` — an assertion this code path cannot make. The gateway never *asks* for a sysctl, but `verify_applied` exists precisely to catch a daemon that answered something other than what was asked; on `ProfileRun`, the one phase running project code under a widened seccomp profile, that is the wrong place to have less coverage than M4.

**Fix.** Make `rust_applied`'s two matrices callable with an M5 phase (or add a `verify_performance` alongside `verify_security`) and delegate, keeping only the M5-specific mount/argv/env/seccomp comparison local.

### P2 — The mandatory permission-denied oracle for M5-03 is not reproducible and is not in the generated receipt

**Files** `/Users/cburgosro/Projects/rust-mcp/crates/execution-adapter/src/performance_native.rs:969-1195`; `/Users/cburgosro/Projects/rust-mcp/docs/validation/M5-03-runtime.json`; `/Users/cburgosro/Projects/rust-mcp/docs/validation/M5-03-profiling-native.json`.

`m5_profile_flamegraph_is_qualified_natively` runs exactly four selections — `profile-positive`, `profile-cpus-sampled`, `zero-sample-control`, `cancellation-during-profiling` — and `M5-03-runtime.json`, the receipt the test itself writes, contains those four and no denial case. `M5-03-profiling-native.json` nevertheless publishes a third case, `denial_control`, with `seccomp: seccomp-rust-quality.json`, `helper_exit: 3`, `perf_errno: 1`. No committed code produces it. Two independent signs that this file is a transcript of a hand-run outside the product path: its zero-sample case records `"argv": ["--zero"]`, which the product cannot emit (the gateway passes the child no argv at all — `performance_gateway.rs:389-402`; the test therefore adds a separate `rust-mcp-profile-zero` bin target, `performance_native.rs:920-967`); and its positive numbers (195 samples, 2154 frames, 198 unresolved, hottest 192) differ from the reproducible receipt's (194 / 2137 / 195 / 193).

**Fix.** Add a selection that drives the denial through `performance_port::profile` (a gateway variant that pins `ProfileRun` to the quality profile, or an equivalent that forces `perf_event_open` to fail), regenerate `M5-03-runtime.json`, and either regenerate `M5-03-profiling-native.json` from that run or relabel it as a manual smoke and mark the denial oracle pending.

### P2 — "Revocable" is claimed with cancel-and-join semantics that no code implements

**Files** `docs/adr/ADR-074-profiling-capability-and-containment.md` §2 ("La capability es por servidor y revocable; su retirada cancela el trabajo en curso, hace join del árbol, conserva la evidencia y devuelve el runtime al perfil calificado"); `/Users/cburgosro/Projects/rust-mcp/SECURITY.md:383-390` (same sentence).

The grant is parsed once from argv (`host_config.rs:84-90`, `:215-219`), stored in `HostConfig.profiling` (`stdio.rs:125`), copied into `profile::Runtime.profiling` (`stdio/profile.rs:156`) and read at `stdio/profile.rs:226-238`. `HostProfilingConfig` is `Copy` and there is no mutation path anywhere in the crate. Revocation is "remove the flag and restart" — which `M5-handoff.md`'s Rollback section states correctly — and a restart does not cancel-and-join anything; a hard stop of the server leaves the operation's containers behind, since cleanup runs in-process.

**Fix.** Either implement runtime revocation (a flag the tool re-reads, with the in-flight operation cancelled through the existing `InspectionControl` and joined by the existing cleanup), or restate ADR-074 §2 and `SECURITY.md` in the handoff's own accurate terms.

Unreachable in practice given the 128-bit nonce.

This is disclosed honestly in `M5-handoff.md` ("Trabajo pendiente: 1. MCP"), which is why it is P3 and not higher.

The reasoning in the application module's header is sound for a single-binary product, but an embedder of `rust_engineering_execution` reaches the profiling gateway without a grant. Defence in depth would put the same check at the port.

## Verified

**Q1 — the sandbox delta is exactly one syscall, in one phase.** I diffed the two profiles structurally, not by prose: identical `defaultAction: SCMP_ACT_ERRNO`, `defaultErrnoRet: 1`, `archMap` (AARCH64 only), and identical rule groups, plus one appended `SCMP_ACT_ALLOW` group whose sole name is `perf_event_open` — 120 unique syscalls vs 121. (ADR-074's prose says the quality profile "permite 121 syscalls"; the file has 121 *entries* across 120 unique names, `clone` appearing in both an unconstrained and an arg-filtered rule. Cosmetic.) `performance_gateway.rs:498-520`: `profiling_profile()` is `self == Self::ProfileRun`, full stop; `exactly_one_phase_selects_the_profiling_seccomp_profile` (`:2897-2918`) asserts that over every phase of every operation, and `profiling_profile_only_adds_perf_event_open` (`:2922-2935`) asserts the JSON delta at the rule level. `create_arguments_for_runtime` (`:698-745`) contains no `--privileged`, no `--cap-add`, no `--sysctl`; `verify_applied` (`:965-975`) rejects a non-empty `CapAdd`, `Privileged: true`, non-empty `Binds`, a second seccomp entry, and a seccomp profile whose parsed JSON differs from the phase's own — with a test that injects `CAP_PERFMON` and one that gives a bloat phase the profiling profile, both rejected (`:3820-3835`). Nothing in the workspace writes `perf_event_paranoid`; the helper's own attr sets `exclude_kernel`/`exclude_hv` (`linux.rs:337-345`) and asks only for `PERF_TYPE_SOFTWARE`/`PERF_COUNT_SW_CPU_CLOCK`. The receipt's two seccomp `sha256` values match the files on disk today (`c288305c…`, `7358b540…`).

**Q2 — the grant.** Three gates, all fed from the same startup argv, none reachable from the peer. `host_config.rs:84-90`: exactly one admissible value, an unknown value fails the whole configuration; `:215-219`: refused unless a Docker runtime is configured. `stdio/profile.rs:222-238`: checked before discovery, before the vendor tree, before the worker. `crates/application/src/profile.rs:127-129`: checked before `capture_security`, with a test that proves zero source captures and zero executor calls when not granted (`:330-341`). `ProfilingGrant` has one variant and no `Deserialize`, so no wire input can produce it. Within the shipped binary the only construction site is `host_config::parse`.

**Q3 — project influence.** `reject_project_cargo_configuration` (`performance_gateway.rs:92-99`) runs before any volume exists, and `domain::security::source_has_cargo_configuration` (`security.rs:39-46`) matches `.cargo/config{,.toml}` at any depth, with a test for nested paths. `VENDOR_SELECTION` (`:79-82`) puts `--config source.crates-io.replace-with="rust-mcp-vendor"` at Cargo's highest precedence, naming the same source the ingested `CARGO_HOME` config declares, so a second definition is a hard Cargo error rather than a silent override. The vendor tree is host-authenticated and its `tree_fingerprint` is recomputed and compared (`:1798-1806`). Every argv is built from constants plus a name matched against `^[A-Za-z0-9_-]{1,64}$` (schema `stdio/profile.rs:63-64`, domain `profile.rs:46-56`); the profiled path is `format!("{TARGET_ROOT}/release/{target}")` (`:246-248`), never analyzer output. The environment is a closed literal list (`rust_gateway.rs:648-660`) with `CARGO_HOME` rewritten and at most one product-owned addition per phase; `CARGO_PROFILE_RELEASE_LTO=fat` comes from a two-variant enum. Mount targets and options are constants. `ProfileBuild` mounts the output volume **not at all** (`:462-467`), so build scripts and proc macros cannot pre-seed `/profile` — which is why the P1 above needs a live grandchild rather than a build-time plant. What the project *does* control and should: which targets exist, `[profile.release]` settings (a `strip` there yields `[unknown]` frames, counted in `frames_unresolved`, not hidden), and the symbols in its own binary.

**Q4 — scope of the helper.** `open_event` (`linux.rs:483-500`) passes `libc::c_long::from(child)` as pid, where `child` is the pid returned by the helper's own `waitpid` on its own fork (`:337-363`); there is no flag, env var or file that names a pid, and `parse_arguments` (`lib.rs:101-174`) has no pid grammar. `waitpid(-1, …)` at `:343` is safe because it runs before `SIGCONT`, when the helper's single forked child is the only process in the namespace. No `ptrace`, no `process_vm_readv`, no `/proc/<pid>` of another task; the fourteen `unsafe` blocks are all in `linux.rs`, each a direct syscall or a fixed-offset atomic read of the mapped metadata page, each with a stated invariant, and `lib.rs` — the whole decoder, ELF parser, sanitizer and serializer — has none. No filesystem path can reach an artifact: `resolve_frame` (`lib.rs:1003-1025`) uses the module path only as a lookup key and returns `UNKNOWN_FRAME` on every failure, and `sanitize_frame` (`lib.rs:983-1001`) maps every byte outside `[0-9A-Za-z_.:$<>,*&\[\]+-]` to `_`, so `/`, `;` and LF cannot survive; `MAX_FRAME_BYTES = 200` bounds it, and because non-alphabet bytes become ASCII `_`, the byte count equals the char count. `profile_stacks::is_allowed_frame_byte` (`profile_stacks.rs:117-134`) re-enforces the same alphabet **host-side** and refuses rather than repairs, so this holds even against a helper that stopped sanitizing. The ELF parser bounds-checks every table (`table_bytes` `lib.rs:806-828`, `section_range` `:885-893`) and `c_string` caps at 4096 bytes; a crafted module yields `[unknown]`, and no non-ELF file's contents can be emitted. The 195-of-2154 unresolved frames in the receipt are declared, not smoothed.

**Q5 — the SVG.** This is a construction property, not a test artifact. `escape` (`profile_svg.rs:172-196`) is total: `&<>"'` become entities, `:` and `=` become numeric references, a leading `h` of `href` (case-insensitive, `starts_href` `:151-163`) becomes `&#104;`, and the catch-all arm maps every non-graphic and non-ASCII char to `_`. Every untrusted string passes through it — `escape(name)` in the `<title>`, `escape(&text)` in the `<text>` (`:296-309`), `escape(plan.title)` twice, `escape(&subtitle)` — and no untrusted text ever lands in an attribute value: the only interpolated attribute is `class="c{palette_index(name)}"`, a `usize` modulo 8. `validate_title` (`:198-206`) restricts the title to ≤120 printable-ASCII bytes. `rendered_bytes_carry_no_active_construct_even_for_hostile_frames` (`:608-651`) uses frame names that are *inside* the sanitized alphabet (`<script>`, `javascript:alert`, `xlink:x`, `<foreignObject>`, `<use>`) plus a hostile title, and asserts the absence of eleven constructs, that exactly one `http://` survives (the namespace), and — via `attribute_names` — that no `on…=` attribute exists whatever the input said. Combined with the parser's alphabet, the input space reaching the renderer is genuinely closed. The byte budget is enforced by re-rendering at a smaller depth, never by truncating mid-element (`:388-427`, tested), and the ceiling cannot be raised by a caller (`:747-758`).

**Q6 — lifecycle.** `_busy = gateway.hold_busy()?` (`:1877`) is bound for the whole function, so capacity is released only after cleanup; `is_quarantined()` and the calibration/verification flags are checked before anything else (`:1878-1884`). The work closure's result is *stored*, not propagated, and the five cleanups run unconditionally afterwards (`:2434-2472`), with `source_cleanup?` … `output_cleanup?` all evaluated before `let work = work?` — so an uncertain cleanup dominates a work error, exactly as G3 requires. Containers are removed before any volume, because `cleanup_until(all_containers, source_volume, …)` is evaluated first and the other four pass `&[]`. `cleanup_until_with_options` (`mutation_gateway.rs:534-589`) and `cleanup_target_until` (`performance_gateway.rs:2519-2557`) both `quarantined.store(true)` and return `CleanupUncertain` on any doubt; `remove_if_present` uses `rm --force` and re-checks absence; cleanup runs under `NeverCancel` with its own deadline, so a cancelled request still gets a full cleanup. `phase_result` (`:421-436`) gives `CleanupUncertain` precedence over both cancellation and timeout. The native `cancellation-during-profiling` selection observed `/opt/perf/bin/rust-mcp-profile-helper` actually running across 586 polls before cancelling, and recorded empty container and volume inventories afterwards (`M5-03-runtime.json`).

**Other things I checked and found sound.** The M5 digest is consistent across `ADR-077`, `performance_port.rs:56-57`, the gateway admission list (`rust_gateway.rs:922-926`) and `host_config.rs:151-156`; `performance_port::admitted` refuses every other image before a container exists, and there is a native selection for that refusal (`performance_native.rs:1300+`). `state.rs` provisions and removes the profile file through the same `openat`/`unlinkat` no-follow path as the other five, and only after `check()` confirms the directory identity. The build is offline (`scripts/build-m5-runtime.py:142` — `docker build --network=none --pull=false --no-cache`, preceded by a mandatory `builder prune --all`, with the reason for the prune documented as a real defect that BuildKit's context snapshot caused). The provisioning receipt's `rust-mcp-profile-helper` sha256 `70fa813d…` matches the one in `M5-03-profiling-native.json`. `decode_profile_tar` (`performance_gateway.rs:1345-1392`) accepts only two fixed regular-file members and refuses symlinks and duplicates, which fails closed against a child that turns `stacks.txt` into a link. `M5-handoff.md` is unusually honest — it states plainly that the tools are not registered, that `tools/list` still returns 27, that the gates have not run, and it lists eight real defects found and fixed, including the two most instructive (`perf_mmap` refusing an inherited `cpu == -1` event, and the profiling seccomp profile never being written to the state dir).

**Q8 — the M5-01 blocker.** Correctly characterized in kind: `execute_operation` ingests `vendor.source` as a `SourceBundle`-backed tar (`:1901`), and `SourceBundle`'s 4096-entry / 16 MiB / 1 MiB-per-file bounds are the M2/M4 offline-data contract shared by `rust.miri`, the security engines and the mutation flows. Refusing to widen them to turn one selection green is exactly right, and `not_done` says so in the correct terms ("No measurement was fabricated and no threshold was lowered"). The evidence for *why no pruning helps* is the weak part (P3 above), and the three negative/control selections that were qualified are real and recorded.

## Limitations of this review

- **Read-only and static.** I ran only `cargo test -p rust-engineering-execution --lib --offline profile` (48 passed). I did not run the gates, Docker, or any `#[ignore]`d native qualification, so I did not reproduce a single M5 receipt. Every claim about guest behaviour rests on the committed receipts plus my reading of the code.
- **The P1 race is reasoned, not demonstrated.** I did not build a hostile fixture that double-forks and rewrites `/profile/stacks.txt`. The preconditions I *did* verify from the files are: `/profile` writable in `ProfileRun`, volume mode `0700` owned by `65534` with the container user `65534`, the helper killing only its direct child, `emit()` writing after that kill and before PID-1 exit, and the host accepting any manifest. The exploitability of the timing window is an inference from those; the deterministic `0444` denial variant is not a race and follows directly from POSIX open semantics.
- **I did not inspect the guest image.** Whether `/opt/rust/bin/cargo` is a rustup shim (which would make a project `rust-toolchain.toml` interesting), whether `/source` exists in the rootfs so a `--read-only` container can use it as `--workdir` when unmounted, and whether the `FROM scratch; COPY --from=builder / /` squash preserved the M4 base's `PATH`/`WORKDIR`/`USER` as ADR-075 §2 claims — all rest on `build.sh`, the Dockerfile and `M5-provisioning.json`, not on the image.
- **I did not review** the criterion dataset/compare statistics (`criterion_dataset.rs`, `benchmark_compare.rs`), the bloat JSON parser, the artifact store's TTL/quota/owner binding, `run_joined_with`'s worker semantics (I read `run_joined_security` and relied on the M3/M4 qualification of the primitive beneath it), or the MCP schemas and their snapshot invariance — all outside the scope I was given.
- **`docs/roadmap/m5-performance.md` changed on disk mid-review**, gaining an "In progress" header that points at the matrix and handoff. I reviewed against the current text; the change is an improvement in accuracy and I have treated it as intentional.
