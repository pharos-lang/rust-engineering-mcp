### P1
**1. Parser grammar is unverified against the pinned rustfmt 1.9.0 binary — this is the single largest correctness risk in the packet.**
`crates/execution-adapter/src/format_output.rs:49-134` hard-codes the exact strings `"Diff in "`, `"Incorrect newline style in "`, and the `path:line:` header shape, sourced only from rustfmt's `main` branch (ADR-035 sources, `docs/adr/ADR-035-format-check.md:56-59`), not the pinned 1.9.0 tag. The packet itself states the real 7-case Docker test (`crates/mcp-server/tests/inspection_runtime.rs:1534`) "is being executed, not yet claiming pass." If the pinned binary's actual wording/format differs even slightly (e.g., trailing punctuation, different newline message text, `at line` vs `:line:`), every real diff will parse as unrecognized. The failure mode is safe (`validation_complete=false` → `Incomplete`, never a false "Passed"/"Failed" with a fabricated diff — confirmed by `finish_chunk`/`complete` handling), so this is not a soundness bug, but it means the feature's actual pass path is unconfirmed. **Action:** treat as blocking until the live Docker run in `inspection_runtime.rs` passes; do not claim platform qualification from static review alone (per instructions).

**2. `CapturedPath` schema regex may reject legitimate filenames the domain layer would happily surface, turning an ordinary result into an encoding failure instead of the designed graceful omission.**
`crates/mcp-server/src/stdio/format.rs:56-63`: `^[A-Za-z0-9_.-]+(/[A-Za-z0-9_.-]+)*$` forbids spaces, non-ASCII, and other filesystem-legal path characters. `format_output.rs` only guarantees the path exists in `SourceBundle` (via `captured_file`/binary_search, `format_output.rs:118-124`); it does not itself restrict the charset. If upstream project capture (not in this packet — `execution-adapter/src/lib.rs`, `project_inspection.rs` capture path) does not already enforce ASCII-only relative paths, a captured file with e.g. a space or unicode name would produce an `affected_files` entry that violates its own output schema. Depending on whether `Contract::encode` (not included in packet) validates structured output against the schema, this could turn into an `internal_error` response for an otherwise-normal format check rather than the intended bounded/omitted degradation. **This is evidence-incomplete** — I cannot confirm from the supplied files whether upstream path capture already restricts to this charset (plausible, given M1-01/M1-02 predate this work) or whether `Contract::encode` even enforces schemas at runtime. Recommend confirming both before considering this closed.

### P2
- **Status conflation between confirmed failure and inconclusive validation.** `crates/mcp-server/src/stdio/format.rs:334-357`: both `CheckOutcome::Failed` (a fully recognized nonempty diff) and `CheckOutcome::Incomplete` (parse/stream/stderr problems) map to the same `Outcome::Failed` tag/`status: "failed"`, distinguished only by `data.validation_complete` and `summary` text. A caller that checks only top-level `status` cannot distinguish "your code is unformatted" from "we couldn't tell." This matches the ADR's stated semantics (exit 1 with unrecognized output is "never passed," and both are legitimately non-passing), and appears to be the same pattern established for `rust.check` in M1-03, so it's not a new regression — but it's worth confirming API consumers are expected to inspect `validation_complete`, not just `status`.

- **Gateway calibration coupling.** `crates/execution-adapter/src/rust_gateway.rs:341-346` inserts `Phase::Run(RustCommand::FormatCheck)` into the single shared sequential calibration list alongside `Metadata`/`Check`/version probes. A calibration failure specific to formatting (e.g., rustfmt binary missing/misconfigured in the image) would fail the entire gateway, taking `rust.check` down with it, not just `rust.fmt.check`. This is consistent with the existing "one calibrated runtime" architecture (not a new design choice), but it does widen the blast radius of a format-specific regression to all tools sharing the gateway. Worth confirming this coupling is intentional/acceptable rather than an oversight.

- **Redundant-but-harmless double bounding.** `crates/mcp-server/src/stdio/format.rs:523-533` re-checks `diff.len() > 32768` and `affected_files.len() > 128` even though `format_output.rs` (`MAX_DIFF`/`MAX_FILES`, lines 8-9, 97-108) already enforces the same limits at the domain layer. Not a bug, just duplicate defense; the byte-vs-character length nuance called out in the comment (`format.rs:522`) is correctly conservative (bytes ≥ chars, so the byte check never lets the char-based schema max be exceeded).

- **Diagnostics-trimming loop in `encode_bounded` is dead code for this tool.** `crates/mcp-server/src/stdio/format.rs:547-572`: format observations always set `diagnostics: Vec::new()` (`crates/execution-adapter/src/project_inspection.rs`, the new `FormatObservation` builder), so the `while !value.diagnostics.is_empty()` loop and the `Passed`→`Failed` downgrade inside it can never execute for `rust.fmt.check`. Harmless (shared scaffolding with `rust.check`'s `Output` shape), but worth a comment or removal if the two tools' output builders ever diverge, to avoid it silently becoming reachable-but-untested logic.
