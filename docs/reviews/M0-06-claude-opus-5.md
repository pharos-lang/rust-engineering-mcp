# M0-06 Security Review — active calibration & explicit CLI

**Scope reviewed:** ADR-025, `crates/execution-adapter/src/{capabilities,applied,lib}.rs`, `seccomp.json`, `crates/mcp-server/src/capabilities.rs`, `crates/application/src/execution.rs`. Read-only; no tools run. Calibration results are taken as reported.

## Verdict

The capability oracles are sound in the direction that matters: every predicate is a positive match over guest evidence conjoined with host-side facts, so missing or corrupted evidence yields `false`, never `true`. Crucially, the guest's self-reported cgroup readings are independently corroborated by `applied.rs` (`PidsLimit==64`, `NanoCpus==5e8`, `Memory==MemorySwap`, tmpfs `size=8m`, `ReadonlyRootfs`, seccomp JSON equality, exact `Env`), and `memory_limited` additionally requires daemon `State.OOMKilled` rather than exit 137 alone (`capabilities.rs:217-225`). `children_contained` is transitively backed by `remove()`'s force-delete plus absence check, which propagates `CleanupUncertain` and aborts the report. The seccomp `clone` mask `0x7E020000` correctly rejects all namespace flags, `clone3`→ENOSYS forces the filtered fallback, and `unshare`/`setns`/`ptrace`/`mount`/`socket`/`memfd_create`/`bpf` are absent from the allowlist. `archMap` lists only AARCH64 with empty subarchitectures, so a 32-bit or wrong-arch caller hits `defaultAction` and fails closed.

**No P0.** I found no path by which a capability is advertised without the corresponding guarantee holding for the pinned configuration.

## P1

**1. `SocketControl` disables seccomp entirely, not "socket creation only."**
`lib.rs:403-405` omits `--security-opt=seccomp=` for `SocketControl`, and `applied.rs:163-167` asserts `seccomp.is_empty()`. The control therefore runs the probe under Docker's *default* profile — a far larger surface than the enforced allowlist (it permits `unshare`, `socketpair`, `openat2`, `personality`, `memfd_create`, `keyctl`, and the full networking syscall set), not merely `socket`. ADR-025:126-129 states the controls "only relax seccomp for socket creation (no connect/send)"; that claim is false as implemented. Two consequences: (a) the control's applied filter content is unverifiable — `container inspect` reports only what was requested, so `applied.rs` can pin *absence* of the flag but not the daemon default's contents; the configuration fingerprint likewise hashes the argv, not the effective filter; (b) the positive control is a weaker discriminator than advertised — it shows "socket() succeeds when our profile is absent", not "our allowlist is the specific cause of denial". Partial mitigations: `ServerVersion` is pinned in `EngineIdentity`, and the enforced denial errno `1` matches `defaultErrnoRet: 1` in `seccomp.json`, which is decent causal corroboration. **Fix:** ship a second profile file that is the enforced allowlist plus `socket` (and nothing else), pass it via `--security-opt=seccomp=`, `include_str!` it into `configuration_identity`, and have `applied.rs` compare applied JSON for that profile exactly as it does for the enforced one. This restores both the narrow-relaxation claim and applied-config verification for the control.

**2. Malformed or truncated probe output produces `unavailable`, contradicting the ADR's own contract.**
`records()` maps every JSON failure to `ExecutionError::Infrastructure` (`capabilities.rs:128,145`), and the batch decode at `capabilities.rs:266-274` uses `?`, so one bad line aborts `probe_capabilities` *after all twelve containers have already run and been removed*. The CLI then emits `status:"unavailable"` with zeroed capabilities and no observations (`mcp-server/src/capabilities.rs:46-57`). ADR-025:122-125 says infrastructure failure emits `unavailable` while "mismatched/failed probes produce degraded". A corrupt or partially-written guest record is a failed probe, not an unreachable daemon. This is exploitable as a legibility/DoS-of-evidence issue rather than a false-positive: the `Descendants` scenario is deliberately killed at 1500 ms and `Output` is deliberately truncated, so trailing partial lines are a realistic failure mode, and every successful observation is discarded. **Fix:** make record decoding per-scenario and non-fatal — drop a trailing incomplete line, treat a mid-stream parse error as that capability being `false`, and still emit a `Degraded` report carrying all observations.

**3. `probe_capabilities` is a public method; CLI-only reachability is asserted, not verifiable here.**
`DockerGateway::probe_capabilities` is `pub` (`capabilities.rs:229`) and `Profile`/`execute_profile` are crate-private, so the control profiles are correctly out of the `ExecutionPort` surface. But any holder of a `DockerGateway` can invoke the calibration suite, including its two relaxed-isolation containers. `crates/mcp-server/src/main.rs` was modified in this change set and is not in the attached files, so I cannot confirm the M0-06 claim that calibration is reachable only from the explicit host subcommand and never from a peer request path. **Action:** confirm that `main.rs` dispatches `capabilities::run` on a distinct argv path that terminates the process, that no `DockerGateway` used for serving is exposed to a handler calling `probe_capabilities`, and that `capabilities_cli.rs` covers the negative case (unknown/duplicate/missing-value flags → no gateway construction). `parse()` itself is sound: pairwise consumption, duplicate rejection via `is_none()`, unknown flag → `None`, and `--probe-image` is later constrained to `sha256:` + 64 lowercase hex (`lib.rs:143-148`), so no argument-injection vector into `docker`.

## P2

- **Socket oracle undersamples.** `network()` requires eight records, but `purpose` (`"dns"`/`"loopback"`) does not affect `socket(2)` arguments — there are only four distinct family×transport tuples, each tested twice, and `seen.len()==8` counts the label as a dimension (`capabilities.rs:185-196`). `AF_UNIX` and `AF_NETLINK` are untested. Both are denied in fact (`socket` and `socketpair` are absent from the allowlist), but the evidence does not show it, and netlink is the classic interface/route enumeration channel. Add those two cases and stop counting `purpose` toward cardinality.
- **Capabilities are booleans that do not carry the budgets they were proven at.** `SandboxEvidence` records ten flags plus one fingerprint; the fingerprint covers all scenarios collectively, and the `Pids` scenario deliberately runs at 256 MiB rather than 64 MiB (`lib.rs:357-361`, `applied.rs:94-98`). `memory_limited` was proven only at 64 MiB. Record the proven numeric budgets in the evidence so a future consumer cannot inherit `memory_limited` for a differently-budgeted scenario.
- **`ioctl` is allowed unfiltered.** Docker's default profile filters `TIOCSTI`/`TIOCLINUX`; this strict allowlist does not. Not currently reachable — `container start --attach` without `-t` gives pipes, not a tty — but it is the one place the profile is looser than the baseline it otherwise exceeds.
- **Duplicated event-name allowlist.** `records()` hardcodes twelve names (`capabilities.rs:129-143`) that duplicate `Event`'s variants, which already have `#[serde(other)]`. Adding a variant without updating the list silently downgrades it to `Event::Other`; today all oracles are positive matches so this fails closed, but it is a latent trap. Drop the list and rely on `#[serde(other)]`, or generate one from the other.
- **Exit-code conflation.** `Degraded` and `unavailable` both exit `1` (`mcp-server/src/capabilities.rs:43,57`), so a shell-driven host gate cannot distinguish "verified, restricted-only" from "no evidence". Use distinct codes (0 strict / 2 degraded / 3 unavailable). Related: the two JSON shapes are non-overlapping — `unavailable` omits `engine`, `image_id`, `configuration_fingerprint`, `observed_at_unix_ms`, `observations` — so document a single discriminated schema keyed on `status`.
- **Minor oracle asymmetries.** `increased()` checks `result.allowed` but not `errno == 0`, unlike `reading()` (`capabilities.rs:198-215`); `fs_ok` bounds record content but not record count, unlike `env_ok`'s `env.len()==1`; `fs_control`/`descendants` are not checked for truncation flags. All fail closed today.
- **Report is unsigned and timestamped with non-monotonic wall clock.** Acceptable only because ADR-025:125 forbids any cached report from authorizing execution. Keep that invariant enforced in code, not just prose, when M1 consumers appear.
- **Operational.** A single `remove()` flake quarantines the gateway mid-suite and blocks the next `new()` via the label scan (`lib.rs:210-225`), requiring manual operator cleanup. Correct and intentional; make sure the runbook says so.
