78:   calificación de enforcement positivo de leases. F_FULLFSYNC devuelve0 para archivo
79:   y directorio, lo que no demuestra supervivencia ante pérdida de energía.

1: # ADR-050 — Mutación local coordinada sin broker privilegiado
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: El owner delegó expresamente la decisión para continuar M2 preservando la esencia
8: local del MCP y evitando una carga de instalación/uso. ADR-049 y su probe demostraron
9: que el UID interactivo no obtiene exclusión kernel frente a otros programas del
10: mismo usuario. Esa garantía adicional del plan D02 no era una capacidad de M1.
11: Exigir un servicio privilegiado, identidad separada o entitlement privado cambiaría
12: la operación de un repositorio ordinario y no es apropiado como requisito M2.
13: 
14: ## Decision
15: 
16: Se adopta **local_coordinated**: edición local coordinada, con permisos explícitos,
17: precondiciones optimistas, publicación por archivo y recuperación conservadora.
18: Es un contrato de confianza distinto de exclusión OS, no un fallback oculto.
19: 
20: 1. Instalación ordinaria del binario, sin daemon, cuentas adicionales, sudo, cambios
21:    de ownership/ACL del proyecto ni entitlement privado. La escritura permanece
22:    deshabilitada hasta un grant de roots/operaciones del host. Configurarlo una vez
23:    selecciona expresamente este modo; no hace falta un checkbox de exclusividad en
24:    cada llamada. El peer no puede conceder ese grant ni cambiar el modo.
25: 2. Se confía en el host y en programas que el developer ejecuta directamente
26:    (editor, Git, shell), como asunción de no hostilidad. El código del proyecto
27:    lanzado por el MCP nunca pertenece a esa clase: solo se ejecuta en el gateway
28:    aislado y un grant de escritura no amplía la autoridad de ejecución. Deben mantener
29:    estables el namespace de roots y el estado privado del servidor, y evitar
30:    escrituras simultáneas sobre archivos afectados durante el commit. El
31:    developer puede trabajar normalmente durante el preview; el digest detecta
32:    diferencias hasta la lectura de validación. Una escritura entre esa lectura y
33:    publicación no se previene y su detección posterior tampoco es universal.
34:    Los locks coordinan instancias que comparten el state root privado ADR-052;
35:    la primera vertical mantiene además un lock global del store durante el commit
36:    para cubrir workspaces anidados. No bloquean IDEs, Git ni escritores externos.
37: 3. Peer, configuración/contenido del proyecto y código ejecutado por Cargo siguen
38:    siendo no confiables. Root handles originales, full relative paths y flags kernel
39:    no-follow/beneath protegen I/O propio; hardlinks/no-regulares se rechazan.
40:    Código del proyecto permanece en el gateway aislado sin bind host escribible.
41:    No se debilitan red, env, cuotas, captura ni permisos de M1.
42: 4. Preview produce candidato/diff/digest exactos únicamente después de que Cargo
43:    valide el candidato en el gateway. Commit rechaza planes cuyo digest no vincula
44:    ese resultado de validación exitoso; no vuelve a generar un candidato distinto. Commit valida grant/principal,
45:    TTL, idempotencia, source generation, root identity y bytes bajo el lock del MCP. Root identity
46:    compara un nuevo open protegido de la ruta host configurada con el handle
47:    original, antes/después de publicar; nunca compara el descriptor solo consigo mismo.
48:    Un conflicto detectado antes del primer efecto no escribe source. Esto no es CAS
49:    por contenido ni snapshot atómico frente a escritores externos.
50: 5. Journal versionado y backups íntegros se hacen durables antes de publicar.
51:    [ADR-052](ADR-052-mutation-journal-and-authorization.md) fija ubicación fuera de
52:    roots, modo 0700/0600, binding de autoridad/idempotencia, cuotas y recuperación.
53:    Durable significa fsync/F_FULLFSYNC exitosos de archivo y directorio; no acredita
54:    supervivencia ante pérdida de energía. Registros esperados ausentes, truncados,
55:    corruptos o no verificables requieren recuperación conservadora, nunca replay
56:    con efectos basado en su ausencia.
57:    Reemplazo usa primitives kernel por archivo, nunca truncado in-place del source.
58:    No hay atomicidad visible multiarchivo, tampoco para lecturas M1 concurrentes.
59:    Después de publicar se verifican bytes e identidades observadas. Cambio desconocido,
60:    root movida o durabilidad incierta lleva a recovery_required y conserva evidencia.
61: 6. No hacer un segundo swap automático para deshacer un conflicto con un editor
62:    externo. La recuperación solo modifica estados identificados como propios y
63:    conocidos, bajo el mismo contrato coordinado; ante bytes desconocidos se detiene.
64:    No se promete conservar en la ruta final una actualización concurrente tardía
65:    mediante un descriptor que otro programa mantenga abierto. Backups y diagnósticos
66:    ayudan a recuperar; no convierten esa carrera en exclusión demostrada.
67: 7. Receipt declara modo, alcance de coordinación, before/after/provenance, cambios,
68:    commit/recovery y limitaciones. Las docs públicas deben explicar el permiso una
69:    vez, el flujo preview→commit y enumerar exactamente los archivos afectados y evitar editarlos durante commit.
70:    Esto incluye checkout/stash/pull/clean y mover la root durante commit. Cambiar
71:    archivos durante preview está permitido: exige preview nuevo si quedan stale.
72:    No auto-stash/reset/commit Git, auto-merge de cambios ajenos ni pérdida silenciosa
73:    de evidencia pendiente para cumplir TTL/cuotas.
74: 
75: Este ADR resuelve la **decisión de producto** D02. No califica todavía un writer ni
76: cierra M2: se requieren tests positivos con root estable/cooperación, y tests de
77: violación del contrato que demuestren rechazos observados y recuperación conservadora.
78: Se conserva el probe anterior como evidencia válida de las garantías que no se ofrecen.
79: 
80: ## Alternatives considered
81: 
82: - Broker privilegiado con UID/namespace exclusivo: ofrece otra frontera, pero añade
83:   instalación administrativa, operación y restricciones al editor; fuera de M2.
84: - Leases privadas XNU: no disponibles para distribución ordinaria y requieren una
85:   calificación adicional de timeouts; descartadas como requisito.
86: - Swap seguido de validación presentado como CAS: incorrecto; el candidato ya fue
87:   visible y el rollback puede desplazar otra actualización. No se acepta ese claim.
88: - Preview-only como M2 final: no cumple las cinco mutaciones normativas.
89: - Escritura optimista sin journal, backup ni permiso: menor trabajo pero protección
90:   insuficiente para los efectos autorizados.
91: 
92: ## Consequences
93: 
94: Se reduce explícitamente la garantía adicional del plan: no se ofrece exclusión de
95: escritores locales arbitrarios ni protección contra un usuario host malicioso. La
96: autoridad de roots y el sandbox frente a proyecto/peer siguen enforced. La UX
97: permanece local, con una configuración de escritura y sin servicio del sistema.
98: Un peer con grant vigente puede mutar el scope autorizado sin una aprobación
99:    humana por archivo: preview/commit vincula el plan, no prueba revisión humana.
100:    Cuotas de escritura/retención son independientes de M1 y rechazan, no truncan.
101: La duración de commit y la tasa de conflictos deben medirse; pausas largas y recovery
102: frecuente son defectos de UX que bloquearían el cierre, no responsabilidad ignorada.
103: Un backend remoto/multiusuario futuro deberá reevaluar esta TCB; no hereda la decisión.
104: 
105: ## Status
106: 
107: Accepted por el Technical Owner bajo la delegación explícita del owner del 2026-09-05.
108: Sustituye la exigencia de exclusión OS fuerte en D02; ADR-049 conserva evidencia histórica.
109: Implementación y calificación positiva completadas: [cierre M2](../validation/M2-07.md).

1: # ADR-052 — Journal privado y autoridad de mutación local
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: ADR-050 requiere publicación recuperable sin convertir un ID de operación en
8: permiso. Los ProjectRef de M1 pueden invalidarse cuando cambia un manifest.
9: 
10: ## Decision
11: 
12: La primera vertical autoriza escritura desde configuración del host por root y
13: operación: --allow-manifest-write ROOT repetible, siempre dentro de --root y coincidente
14: exactamente con la raíz del workspace a editar; no concede subproyectos implícitos.
15: Exige la policy runtime existente para validar el candidato; no añade instalaciones. El principal local es el UID que inicia stdio; el canal stdio y su host
16: son la frontera de identidad, no clientInfo ni valores aportados por el peer.
17: Un receipt requiere reabrir el proyecto y una referencia viva autorizada por el
18: grant actual para la misma identidad física y operación. Revocar el grant impide
19: nuevos commits y consultas por MCP; no borra evidencia privada. No hay autoridad
20: multiusuario o remota implícita.
21: 
22: Preview exige la identidad de manifests observada al abrir y produce la generación
23: completa del source que se aprueba con el digest de commit. No exige al peer un
24: hash nuevo que ninguna tool M1 suministra antes del preview.
25: 
26: Planes en memoria: TTL 600 s monotónico, ID aleatorio de 128 bits, máximo cuatro
27: planes y 64 MiB de bytes agregados; se invalidan al reiniciar. Preview captura
28: source completo, produce candidato inmutable y digest con separación de dominio
29: que incluye paths/bytes antes/después, operación y contexto de validación.
30: Commit exige ID/digest y clave idempotente; reuso con distinto digest falla.
31: La pérdida de respuesta se resuelve mediante receipt del ID original.
32: 
33: El journal versionado conserva bytes before/after y la clave/digest antes del
34: primer efecto. Estado privado del UID, directorios 0700 y archivos 0600 fuera de
35: las roots de proyecto; no se acepta symlink/hardlink ni ownership ajeno. La primera vertical usa el hijo fijo rust-mcp-mutations-v1 del --state-root
36: existente del gateway, creado 0700 mediante handles protegidos. No añade una
37: segunda ruta de configuración ni usa HOME del peer. El proceso no requiere
38: privilegios ni cambia permisos de directorios ajenos. Todas las instancias que
39: escriben el mismo workspace deben compartir ese --state-root.
40: 
41: Orden de adquisición no bloqueante: global del store → device/inode del workspace.
42: Ambos se conservan hasta completar persistencia/cleanup; se rechaza busy sin cola.
43: El global serializa también workspaces distintos/anidados del mismo store.
44: Un lock por device/inode del workspace serializa writers MCP con
45: el mismo state root. Todos los procesos MCP que escriben un workspace deben usar
46: ese mismo state root; cambiarlo con operaciones pendientes está fuera del contrato
47: coordinado y se documentará en configuración. No se promete exclusión entre stores
48: independientes ni ante otros programas.
49: 
50: Primera publicación calificada: reemplazos de archivos existentes, máximo 128,
51: 1 MiB por archivo/16 MiB source. Temporales exclusivos .rust-mcp-mut-<32 hex>.swap en la raíz exacta del workspace
52: (clone APFS del source admitido para preservar metadata; solo se reescriben bytes
53: del clone), para no
54: exigir que el state root esté en el mismo volumen; paths completos relativos al
55: handle original y renameatx_np NOFOLLOW_ANY|RESOLVE_BENEATH|SWAP. La copia before
56: en el journal es durable antes de crear/publicar. El temporal tras swap retiene
57: el inode desplazado; se verifica antes de limpiar. Solo se retira un temporal
58: propio identificado por inode/bytes bajo el lock después del journal durable.
59: El unlink usa un nombre simple en el handle original del workspace exacto, sin
60: componentes intermedios que puedan seguir symlinks. Éxito no deja temporales.
61: La creación de clone y su reescritura son fases distintas: el inode del clone se
62: registra duramente antes de truncarlo. Antes de cualquier publicación, ese inode
63: es scratch exclusivo del protocolo; una escritura parcial/ENOSPC puede retirarse
64: solo si el source original conserva sus bytes e inode y la fase durable no permite
65: que el temporal contenga source desplazado. El host y sus herramientas no editan
66: los nombres reservados `.rust-mcp-mut-*`, tampoco después de una interrupción.
67: Si el proceso cae entre clone y registro del inode, recovery solo puede adoptar
68: el clone con bytes before exactos, metadata/owner/nlink válidos y source intacto,
69: bajo el intent durable de creación exclusiva; cualquier otra observación conserva
70: recovery_required. Tras habilitar/publicar swap, la regla estricta de bytes/node
71: conocidos para el source desplazado vuelve a aplicar: no tratarlo como scratch.
72: Si hay recuperación pendiente no ejecutar git clean/add ni eliminar esos archivos. No rollback automático por un
73: conflicto externo. fsync y F_FULLFSYNC de archivo y directorio son obligatorios;
74: cualquier incertidumbre posterior a publicación da recovery_required.
75: 
76: El ID del preview se persiste como operation ID en el journal antes de publicar.
77: Receipt tras restart usa ese ID durable y nueva referencia viva/grant; no requiere
78: el plan en memoria. La recuperación se solicita explícitamente en receipt con
79: recover=true; un commit pendiente también debe clasificar conservadoramente. Sin
80: grant no se inspecciona ni repara estado por MCP: devuelve permission_denied y las
81: docs indican conservar cualquier evidencia pendiente y reiniciar con el mismo
82: grant/state-root. No se anuncia que una sesión sin grant haya comprobado recovery.
83: 
84: La recuperación clasifica archivos como before/after/desconocidos y solo completa
85: estados conocidos bajo el mismo grant/lock. Desconocidos conservan journal y
86: temporales, sin escritura de source. Cancelación se atiende antes del primer
87: efecto; después se termina la persistencia del resultado o recovery_required.
88: No anunciar commit successful antes de la persistencia del receipt. Un candidato
89: idéntico produce no_change; una operación interrumpida sin publicación produce
90: aborted y exige otro preview. El recibo distingue los hashes previstos del efecto
91: terminal registrado: committed acredita after, aborted/no_change acredita before,
92: y recovery_required no acredita un after. No afirma que ningún escritor posterior
93: haya conservado esos bytes. Consultar un recibo no promueve ni repara staging;
94: recover=true es la acción explícita para reconciliarlo. Las consultas y recovery
95: por ID autorizado permanecen disponibles ante cuota llena o entradas ajenas del
96: store; esas condiciones bloquean trabajo nuevo, no la recuperación conservadora.
97: 
98: El preview libera el registry de referencias durante el oráculo Cargo y recaptura
99: su generación al terminar. La admisión M2 no espera el mutex de otra mutación;
100: responde lock_busy. El payload MCP completo se mide antes de retener el plan.
101: 
102: Cuotas iniciales: 128 journals y 256 MiB totales por store, entrada serializada
103: máxima 48 MiB. La cuota se verifica bajo lock global antes de comenzar; no borrar
104: journals pendientes por TTL. La ubicación es <state-root>/rust-mcp-mutations-v1; store lleno devuelve
105: limit_exceeded. No borrar el directorio completo. La CLI administrativa local
106: `mutation list --state-root ROOT` enumera IDs/digests/estados/tamaños sin source;
107: `mutation prune --state-root ROOT --operation-id ID --plan-digest SHA` retira solo
108: un journal terminal validado, con cleanup ya acreditado en su fase durable, y exige
109: confirmar el digest exacto. Rechaza pendientes, staging, versión desconocida o
110: corrupción; no ejecuta Cargo ni toca source. La autoridad es el operador local/UID
111: del state root, separada del peer MCP: no es otro modo de la tool ni un ID bearer
112: para consultas MCP. No requiere que el workspace original todavía exista para
113: eliminar un recibo terminal. Conserva lock global y fsync/fullfsync del store.
114: La CLI no crea el store al consultarlo ni al limpiarlo. No hay retención automática.
115: Prune elimina evidencia e idempotencia durable de ese ID; antes de usarlo el operador
116: debe haber consumido el recibo y descartado sus planes. Reintentar una mutación
117: purgada requiere otro preview. La CLI debe calificarse antes de M2-01 Done.
118: 
119: La admisión reserva además espacio global para reescribir cualquier journal
120: existente: el total retenido después de admitir el nuevo registro no supera
121: 207 MiB: 256 MiB menos 48 MiB para un staging máximo y 1 MiB para crecimiento de metadata de hasta 128 registros (8 KiB por registro, incluida conversión legacy). Esta reserva cubre la copia staging
122: de recovery aun si registros pequeños llenan después el store. La reserva de dos
123: records de peor caso por commit sigue aplicando; se cumplen ambas condiciones.
124: No se borra evidencia para recuperar capacidad. El techo no es retroactivo: stores
125: de checkouts 0.2.0-dev poblados bajo el techo anterior de 208 MiB no adquieren
126: automáticamente esta holgura; no se migran ni purgan. Recovery por ID permanece
127: separado del scan global, que puede rechazar un máximo transitorio.
128: 
129: Un journal parcial o corrupto no es un sucesor validado. Se conserva y puede
130: bloquear todo el store compartido: list/prune y commits nuevos fallan cerrados;
131: receipt/recovery del ID afectado no garantizan convergencia automática. Esto también
132: puede ocurrir por interrupción propia durante escritura, sin actor externo. La
133: recuperación por ID de otros registros íntegros no escanea el store completo.
134: 
135: Remediación soportada ante corrupción persistente: detener TODAS las instancias
136: que comparten ese state root; preservar sin cambios el store original y todos los
137: workspaces afectados, incluyendo temporales. Preparar un workspace físicamente
138: nuevo en otra ruta a partir de contenido cuya generación el operador haya revisado,
139: sin trasladar temporales reservados ni tratar bytes dudosos como resultado aprobado.
140: Configurar un state root privado NUEVO y grants explícitos únicamente para las
141: nuevas copias; nunca apuntar el store nuevo a los workspaces originales aún en
142: cuarentena. Reabrir y generar previews nuevos. Los originales siguen disponibles
143: para reconciliación manual; no se elimina ni edita un journal corrupto, no se fuerza
144: prune y no se transfiere idempotencia a la identidad física nueva. Esta salida
145: restaura operación en la copia, NO repara ni certifica el registro original.
146: El procedimiento se aplica por cada workspace que deba continuar, incluidos los
147: que solo estaban bloqueados: sus recibos e idempotencia permanecen en el store
148: en cuarentena.
149: 
150: Esta limitación de disponibilidad se acepta como P2 residual antes de M2 Done
151: solo con prueba reproducible de propagación del bloqueo y de continuación aislada,
152: publicación del procedimiento y revisión independiente de la disposición. Evita
153: un borrado automático o nueva CLI de salvage que convierta bytes incompletos en
154: autoridad. Mejorar convergencia requiere otro diseño explícito de conservación y
155: clasificación de evidencia; no queda oculto como recuperación universal.
156: 
157: ## Alternatives considered
158: 
159: - IDs bearer: simplifican lookup pero conceden autoridad por conocimiento del ID.
160: - Journal en el proyecto: expone evidencia privada al contenido/código del proyecto.
161: - Locks por ProjectRef: permiten dos instancias sobre el mismo workspace físico.
162: - Estado distinto por instancia: rompe coordinación de múltiples procesos.
163: - Commit sin persistir before: no permite recuperación verificable.
164: 
165: ## Consequences
166: 
167: La configuración por usuario debe compartir state root. Un store lleno rechaza
168: antes del source; no se elimina evidencia para conseguir espacio. Los receipts
169: durables y los artifacts efímeros M1 tienen lifecycle distinto. La creación de
170: ADR-054/055/057 califican el reemplazo conjunto de manifests y un Cargo.lock
171: ya existente; la creación de Cargo.lock en el host queda fuera de M2.
172: 
173: ## Status
174: 
175: Primera calificación nativa: macOS 26 ARM64/APFS; otros hosts rechazan antes de I/O.
176: El límite de 256 KiB del editor se aplica a manifests antes del límite general 1 MiB.

1: # ADR-053 — Staging de mutación acotado en el runtime existente
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: M2-02/03 necesitan que rustfmt/Cargo modifiquen una copia, sin write bind del host.
8: El volumen local ordinario de M1 no limita disco. Un tmpfs por contenedor pierde
9: sus bytes al terminar y no sirve para exportar después de eliminar mutadores.
10: 
11: ## Decision
12: 
13: Extender el único Execution Gateway con fases tipadas M2. Usar la imagen aprobada
14: existente y un volumen Docker local-driver con type/device tmpfs y opciones exactas
15: `size=64m,nr_inodes=8192,uid=65534,gid=65534,mode=0700,nosuid,nodev,noexec`.
16: Un guardian confiable `/usr/bin/sleep 900`, sin red y con mount read-only, mantiene
17: una referencia activa durante todo el job. No es un servicio instalado ni persistente.
18: Verificar identidad/estado running antes de transferir y después de cada mutador.
19: No reiniciar automáticamente el guardian: perder su mount invalida el candidato.
20: 
21: Orden: volumen → guardian → ingest confiable → mutador tipado → remove y ausencia
22: verificada de todos los writers → exporter confiable read-only → cleanup exporter,
23: mutadores, guardian y volumen → ausencia verificada. Cualquier incertidumbre de
24: cleanup pone el gateway en cuarentena. Se reutilizan identidad del daemon, imagen,
25: seccomp, env reconstruido, UID65534, budgets, supervisión y cancellation de M1.
26: Solo ingest de archivo generado y fase mutador pueden montar source RW. No añadir
27: comandos libres ni shell. Las trece tools M1 mantienen sus perfiles read-only.
28: 
29: Ingest M2 genera USTAR propio, dirs0700/files0600. Exporter fijo:
30: `/usr/bin/tar --create --file=- --format=ustar --sort=name --one-file-system --directory=/source .`.
31: Exigir exit0, stderr vacío, stdout completo y acotado24MiB. Decodificar en memoria,
32: nunca extraer en el host: validar checksum, tipos regular/directorio, nombres
33: portables y únicos, modes esperados, UID/GID65534, sin links, devices, PAX/GNU,
34: sparse, paths externos, colisiones ni datos extra tras fin. Admitir únicamente
35: prefijo generado `./` y slash terminal de directorio, sin normalización general.
36: El source resultante conserva exactamente paths/tipos/directorios de la captura;
37: el validador de operación decide los bytes cambiables. fmt/fix solo `.rs` existentes.
38: Crear Cargo.lock se diseñará/calificará por separado en D05 y el writer nativo.
39: 
40: Los 64MiB/8192inodes limitan staging y deben probarse contra source máximo de M1
41: (16MiB/4096entradas), rustfmt y fixtures Cargo. No implican que todos los proyectos
42: sean aceptados: agotamiento aborta y limpia, sin publicar un candidato parcial.
43: El límite interno binario es independiente del límite de texto del resultado MCP.
44: Las fases/argv/config/versiones y source exacto se vinculan al fingerprint de ejecución.
45: 
46: ## Alternatives considered
47: 
48: - Host bind RW: permite a código de proyecto alcanzar source real; rechazado.
49: - Volumen Docker ordinario: no ofrece cuota de bytes/inodos acreditada; rechazado.
50: - Exportar desde el mutador vivo: productor hostil puede competir con export; rechazado.
51: - Otro runtime/helper instalado: añade distribución y mantenimiento innecesarios.
52: - Un tmpfs por contenedor o contenedor detenido como guardian: pierde continuidad.
53: 
54: ## Consequences
55: 
56: El control plane M2 usa un deadline compartido de trabajo y una reserva de cleanup
57: de 10 s desde su inicio, sin renovar 10 s por comando. La reserva ignora la

1: # ADR-054 — Publicación de varios archivos existentes
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: M2-01 califica un lint del manifest raíz. fmt.apply necesita reemplazar varios
8: `.rs`, incluidos descendientes. Guardar un journal completo por cada archivo y
9: fase multiplicaría innecesariamente el I/O; el journal ya contiene bytes y nodos
10: suficientes para reconocer cada lado de un swap tras un crash.
11: 
12: ## Decision
13: 
14: Generalizar el publisher nativo a una lista ordenada de hasta128 reemplazos de
15: archivos existentes. Cada elemento liga path, source node, staged node y temporal
16: exclusivo `.rust-mcp-mut-<id>-<index>.swap` situado en la raíz exacta autorizada.
17: Los destinos descendientes se resuelven completos desde ese root original con
18: NOFOLLOW_ANY/BENEATH; cleanup solo usa hojas de temporales en ese mismo handle.
19: El writer queda ligado a una operación autorizada: manifest_patch o format_apply.
20: Un grant de formato no concede patch de manifest ni consulta de sus receipts.
21: 
22: El kind de formato verifica alcance, tamaños y bytes aprobados en la frontera
23: nativa; no interpreta semántica Rust ni acredita por sí solo el origen rustfmt.
24: Esa evidencia procede del productor aislado y su postcheck, ligados al digest por
25: la aplicación. SourceBundle ordena paths y SourceFile impone 1 MiB por archivo;
26: son invariantes del dominio, adicionales a las comprobaciones del publisher.
27: 
28: Fases globales: Prepared → Scratch → Staged → Applying → Published → Committed.
29: Aborted/NoChange y RecoveryRequired conservan la semántica de ADR-052.
30: 
31: 1. Capturar full source y verificar generación, operación y todos los nodos.
32:    Reservar cuota y persistir plan/before/after/paths/temp intents antes de efectos.
33: 2. Crear todos los clones exact-before sin truncarlos. Persistir todos sus inodes
34:    en Scratch antes de reescribir cualquiera. Prepared interrumpido puede adoptar
35:    solo clones exact-before bajo las reglas de ADR-052; si falta un clone, no hay
36:    obligación de crearlo durante recovery: conservar original y abortar/limpiar.
37: 3. Reescribir/verificar todos los clones y persistir Staged. En Scratch, con todos
38:    los originales intactos y nodes propios durables, los temporales son scratch.
39: 4. Verificar nuevamente la generación completa excluyendo únicamente temporales
40:    propios de esta operación por nombre exacto + inode. Persistir Applying antes
41:    del primer swap; publicar en orden y verificar cada pareja de bytes/inodes.
42: 5. Cuando todo source coincide con after, persistir Published antes de limpiar
43:    originales desplazados. Retirar solo temporales verificados; persistir Committed
44:    después de cleanup durable. El recibo no anuncia éxito antes de ese punto.
45: 
46: No hace falta reescribir el journal completo tras cada swap: los nodos registrados
47: antes del primer efecto y cada pareja activa/temporal distinguen un prefijo after
48: y un sufijo before. Tras una interrupción sin efectos se aborta sin publicar.
49: Con un prefijo ya publicado, recovery puede completar el sufijo aprobado únicamente
50: cuando toda la generación lógica coincide con ese estado mixto conocido, incluidos
51: archivos no editados. No se vuelve a ejecutar rustfmt/Cargo ni se calcula otro diff.
52: Unknown, orden incompatible, source ajeno modificado, nodo cambiado o temporal
53: perdido antes de Published dejan RecoveryRequired y no activan rollback ni avances.
54: En Published, temporales ausentes representan cleanup ya efectuado y se conservan
55: los checks de source after y nodos antes de retirar los restantes.
56: 
57: Cancelación anterior al primer efecto aborta. Tras el primer efecto se termina
58: publicación/cleanup o se conserva recovery_required; no se devuelve cancelled por
59: una operación que ya publicó. Los locks global/shard se mantienen hasta finalizar.
60: La captura lógica excluyente es privada del writer y exige los nodos exactos del
61: journal: no altera ProjectSourceBackend::source ni el comportamiento M1 y no acepta
62: patrones de exclusión aportados por el peer.
63: 
64: Usar journal v2 para nuevas operaciones. Conservar un decoder estricto de v1 y su
65: checksum sobre el cuerpo v1 original; solo después de verificarlo se representa
66: internamente como una operación manifest de un archivo. Receipt/list no migran.
67: La recuperación explícita o replay de commit autorizado pueden persistir ese
68: registro en v2 bajo los mismos locks; antes de ello se conservan las reglas v1
69: de reconocimiento, especialmente Staged que pudo publicar antes de interrumpirse.
70: Un formato desconocido nunca provoca efectos ni limpieza. No se admite downgrade
71: del writer experimental después de escribir v2. Ninguna release publicada contiene
72: aún writer. Los registros experimentales deben consumirse/prunearse antes de
73: volver a un checkout antiguo; no hay migración automática al iniciar el MCP.
74: 
75: El host concede formato mediante `--allow-fmt-write WORKSPACE_ROOT`, separado de
76: `--allow-manifest-write`. Ambos requieren el runtime aprobado y journal externo a
77: las roots. Cada instancia del publisher liga exactamente un MutationKind; la
78: lectura/recuperación MCP verifica también ese kind. La CLI administrativa local
79: puede enumerar/prunear registros terminales de ambos tipos bajo su autoridad UID.
80: El payload completo se escribe por fase global, no por archivo: costo de journal
81: acotado por fases × bytes del plan. Medirlo con source/cantidad máximos antes de Done.
82: 
83: La reserva se calcula con la codificación del peor estado de fase (todos los nodos
84: temporales presentes, coordenadas/tamaño decimal máximos, contador de secuencia
85: máximo y nombre de fase más largo), no con un margen constante sobre Prepared.
86: Se rechaza antes de crear journal/temporales si ese estado no cabe en 48 MiB o
87: si sus dos copias transitorias no caben en la cuota del store.
88: 
89: ## Alternatives considered
90: 
91: - Un commit independiente por archivo: oculta efectos parciales al contrato del plan.
92: - Reescribir todos los bytes de journal después de cada archivo: I/O proporcional
93:   a archivos × tamaño total, innecesario cuando el estado de swaps es reconocible.
94: - Rollback inverso automático: podría desplazar bytes externos; rechazado.
95: - Ignorar globalmente `.rust-mcp-mut-*` durante source capture: ocultaría archivos
96:   ajenos y cambiaría M1; solo se excluyen nodes propios exactos en captura interna.
97: - Publicar archivos nuevos/Cargo.lock: requiere otra primitiva, fuera de este corte.
98: 
99: ## Consequences
100: 
101: La recuperación puede completar efectos ya aprobados en un plan parcialmente
102: publicado; se conserva la promesa de no publicar una generación desconocida.
103: La operación no es visible atómicamente a IDEs ni otros lectores. El namespace
104: confiable y nombres reservados de ADR-050/052 siguen siendo condiciones del host.
105: Sin la nueva captura lógica y pruebas de crash por prefijo no se habilita fmt.apply.
106:

1: # ADR-055 — Datos Cargo offline y preservación de la presencia del lock
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: Add/remove y ciertos cambios de features necesitan resolver dependencias. El
8: catálogo SQLite no es un registry Cargo. M1 usa CARGO_HOME vacío y ninguna tool
9: puede descargar datos. D05 comparó dos fuentes reales con Cargo 1.98.1 del image
10: aprobado: local registry y directory source, incluyendo alias, features, optional,
11: transitivas y datos ausentes/corruptos.
12: 
13: Directory source requiere más bytes/archivos en el fixture, pero su productor
14: `cargo vendor` ya forma parte de Cargo. Evitar otra instalación pesa más que esa
15: diferencia acotada de ingest. El probe detectó que metadata puede aceptar un
16: Cargo.toml vendorizado alterado; por tanto no prueba integridad del dataset.
17: 
18: ## Decision
19: 
20: Usar directory source provisto explícitamente por el host, optativo para las
21: operaciones que requieren dependencias. No afecta instalación ni uso M1, lints o
22: fmt. El operador prepara fuera del MCP un directorio mediante Cargo habitual:
23: 
24: ```text
25: cargo vendor --locked --versioned-dirs /ruta/privada/vendor
26: rust-engineering-mcp cargo-vendor inspect --directory /ruta/privada/vendor --json
27: ```
28: 
29: El primer comando es una instrucción administrativa para el desarrollador, no una
30: invocación automática del runtime MCP. Para agregar crates nuevas, el operador
31: incluye versiones aprobadas en un manifest de provisioning con su lock; vendor de
32: la lock actual solo contiene las dependencias ya resueltas. Se admite el `--sync`
33: habitual de Cargo para agrupar manifests de provisioning. No se añade ni copia la
34: configuración generada por vendor al proyecto.
35: 
36: El host configura el par cerrado `--cargo-vendor-dir PATH` y
37: `--cargo-vendor-tree-sha256 sha256:DIGEST`. La CLI inspect captura/verifica el árbol
38: y devuelve digest, conteos y paquetes, sin ejecutar Cargo ni descargar nada. No
39: retorna bytes de source. El runtime captura esos mismos bytes mediante handles
40: no-follow, verifica el digest esperado y conserva el valor inmutable usado por el
41: gateway; no valida por hash y vuelve a abrir los paths después. El dataset queda
42: fuera de las roots de proyecto y nunca se monta por bind desde el host.
43: 
44: Límite inicial: 16 MiB, 4096 archivos/directorios, 1 MiB por archivo y el mismo
45: subconjunto portable de paths de SourceBundle. Es una fuente selectiva aprobada,
46: no import de todo CARGO_HOME. Se rechazan links, hardlinks, archivos especiales,
47: ownership ajeno, escritura group/other, cambios durante captura y layout fuera
48: del contrato antes de Cargo. Directorios e inodes se revalidan; sin adapter nativo
49: protegido no se inspecciona el filesystem. El árbol es de datos, no de proyectos:
50: su captura no relaja ni reutiliza las exclusiones de configuración Cargo de M1.
51: 
52: Cada paquete de primer nivel contiene Cargo.toml y `.cargo-checksum.json` estricto.
53: Se verifica cada archivo listado, su SHA-256 y ausencia de archivos extra salvo el
54: checksum. Todos los paths son relativos al paquete; no duplicados ni escapes.
55: Se exige `package` checksum SHA-256 no nulo para paquetes crates.io; Git y registries
56: alternativos quedan fuera de este corte. Nombre/version de Cargo.toml deben ser
57: válidos, únicos como pareja, y coincidir con el directorio versionado. El digest
58: de árbol cubre paths ordenados y bytes con longitud u64 little-endian, igual al
59: probe D05. Se rechazan directorios no implícitos en los paths de archivos: así la
60: topología autorizada queda determinada por esos paths, sin directorios vacíos
61: adicionales fuera del digest. Checksum es control de integridad; la autorización de esos bytes procede
62: del fingerprint esperado por el host, no del checksum autoafirmado por el paquete.
63: 
64: El gateway ingiere los bytes aprobados en un volumen tmpfs separado acotado, con
65: guardian y lifecycle de ADR-053; tras ingest no quedan escritores y todos los jobs
66: Cargo montan los datos read-only. Solo argv/config constantes del gateway activan
67: crates-io→directory source. Network none, HOME/CARGO_HOME efímeros y ninguna credencial.
68: Resolver usa metadata offline en staging escribible y luego metadata frozen sobre
69: esa resolución. Un fallo descarta el candidato completo, incluso cuando Cargo
70: alcanzó a escribir Cargo.lock. La validación liga dataset, runtime, ambos comandos
71: y hash del lock resuelto, sin afirmar que resolvió lo más reciente en Internet.
72: 
73: Política host de M2: `preserve_presence`. Si Cargo.lock existe, actualizarlo junto
74: con los manifests en el mismo plan. Si no existe, usar un lock transitorio durante
75: resolución/validación y excluirlo explícitamente del candidato publicable, dejando
76: constancia de ese hecho y de su hash. Se conserva la elección observable del repo;
77: no se infiere application/library de targets ni se crean archivos host nuevos.
78: La forma de exportación agrega una entrada esperada para el lock transitorio;
79: un source sin lock que ya ocupe las 4096 entradas falla cerrado por límite antes
80: del job. Metadata completa tiene límite de salida de 1 MiB por stream; truncación
81: impide validar y nunca produce candidato parcial.
82: Cargo crea el lock nuevo con modo 0644. La entrada de decoder específica de
83: resolución admite ese modo únicamente para el Cargo.lock raíz transitorio, con
84: los mismos controles de nombre/tipo/UID/GID/checksum/límites; ese archivo se retira
85: del candidato antes de publicar. Un lock preexistente y todos los demás archivos
86: siguen exigiendo 0600. No se amplía el decoder de fmt/fix ni se normalizan permisos
87: de bytes desconocidos en el host.
88: El preview/receipt declara esta policy. La validación no promete que una futura
89: lectura M1 frozen sin lock pueda resolver; los comandos M1 conservan su contrato.
90: No se permite manifest-only silencioso cuando faltan datos: devolver un resultado
91: operacional `unavailable` con razón `offline_data_missing` e `isError: true` y no publicar. Datos corruptos permanecen `blocked` con `offline_data_invalid`; un fallo Cargo del candidato permanece `failed`. Esto concreta la distinción de disponibilidad de D01 sin cambiar enums ni schemas M1.
92: 
93: La validación de ambos documentos metadata acredita cada manifest de paquete
94: contra bytes capturados bajo `/source` o el dataset aprobado bajo `/rust-mcp-vendor`.
95: Las identidades de paquetes vendor deben coincidir con el inventario verificado;
96: paquetes locales y patches dentro del source siguen ligados al fingerprint completo
97: del proyecto. No se describe todo el grafo como procedente del vendor. Se compara
98: la resolución con la revalidación frozen y sus documentos quedan ligados por SHA
99: al fingerprint de ejecución, junto al decoder de export. La ausencia identificable
100: de un crate/versión en el directorio offline devuelve un motivo de datos ausentes;
101: no dispara descargas ni acepta un lock sin ese oráculo.
102: 
103: ## Alternatives considered
104: 
105: - Local registry: compacto y calificado como fixture, pero exige otro productor o
106:   implementar su administración. Se conserva como evidencia, no como instalación.
107: - Importar CARGO_HOME: incorpora configuración, credenciales, red y estado mutable.
108: - Descargar automáticamente durante preview: rompe offline-first y la autorización
109:   explícita del host.
110: - Crear Cargo.lock por defecto en cualquier repo: impone una decisión al developer
111:   y exige ampliar la primitiva nativa de publicación. Preservar presencia evita
112:   ese cambio; una futura policy de creación requiere ADR/calificación propia.
113: 
114: ## Consequences
115: 
116: El camino habitual mantiene cero servicios instalados adicionales. Solo quien use
117: resolución offline administra un dataset Cargo seleccionado. Los límites iniciales
118: son explícitos; no se anuncian workspaces arbitrarios ni soporte cross-platform
119: positivo. El dataset puede contener código ejecutable por build.rs/proc macros;
120: verificar sus bytes no lo convierte en confiable fuera del sandbox.

1: # ADR-056 — Cargo fix y coordinación interna aislada
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: Cargo 1.98.1 usa un servicio TCP para coordinar la aplicación de fixes. El probe
8: D06 demuestra que el perfil seccomp existente deniega ese mecanismo, y que
9: `--default-features` no es un flag válido de cargo fix en esta versión. El owner
10: pidió continuar M2 sin añadir servicios instalados ni carga de configuración.
11: 
12: ## Decision
13: 
14: Aceptar una variante tipada `Fix` del productor de candidatos del Execution
15: Gateway. Reutilizar staging, exportación estricta, cuotas y cleanup de ADR-053,
16: el publisher de reemplazos existentes de ADR-054 y la imagen ya aprobada. No
17: añadir ejecutable host, daemon persistente, flags libres ni instalación adicional.
18: 
19: Invocación fija:
20: 
21: ```text
22: /opt/rust/bin/cargo fix --workspace --all-targets --frozen --offline --allow-no-vcs --allow-dirty --allow-staged --message-format=json --color never --target-dir /target
23: ```
24: 
25: Las features por defecto se seleccionan omitiendo flags de features. M2 no ofrece
26: edition migration, broken-code, selección arbitraria de targets ni argumentos
27: Cargo. Los permisos VCS se refieren exclusivamente a la copia capturada sin .git;
28: el plan conserva y compara los bytes dirty reales, sin reset, stash ni commit Git.
29: 
30: Solo esta fase usa un perfil seccomp dedicado incorporado al binario y verificado
31: contra la configuración aplicada: perfil existente más `socket` AF_INET,
32: SOCK_STREAM, protocolo 0 y `bind`, `connect`, `listen`, `accept4`, `getsockname`,
33: `setsockopt`, `shutdown`. Sigue `network=none`, sin interfaces externas, host
34: network, socket Docker, secretos ni bind host. Se permite TCP en loopback dentro
35: de su namespace; no afirmar denegación absoluta de sockets ni autenticidad de los
36: mensajes internos de Cargo. No ampliar el perfil M1, fmt, ingest ni exporter.
37: La comparación de tipo usa `SCMP_CMP_MASKED_EQ` con máscara 15 y datum 1: el tipo base debe ser SOCK_STREAM, conservando flags CLOEXEC/NONBLOCK. El probe del filtro aplicado confirmó que el orden inverso 1/15 permitía tipos impares llegar al kernel; no impedía STREAM. Se corrige la precisión de la policy, sin ampliar protocolos ni familias.
38: El target de compilación es tmpfs ejecutable, acotado y separado de source.
39: 
40: Éxito exige exit 0, captura completa acotada, OOM false, JSON Cargo válido con
41: build-finished success, export completo y cleanup confirmado. Stderr admite
42: progreso normal acotado. Después ejecutar `cargo check` frozen independiente sobre
43: el candidato, con el perfil M1. Una salida no cero, malformed, timeout, cancelación,
44: overflow, cambio de scope o incertidumbre descarta todos los bytes candidatos.
45: 
46: `rust.fix.apply` usa preview/commit/receipt y permiso host separado
47: `--allow-fix-write WORKSPACE_ROOT`. Solo puede reemplazar hasta 128 archivos `.rs`
48: existentes; manifests, lock, directorios y paths permanecen idénticos. Inicialmente
49: requiere lock existente aceptado por Cargo frozen. La autoridad y el digest son
50: de tipo `fix_apply`; no se aceptan planes o receipts de otra operación. El recibo
51: liga fingerprints del mutador y check, runtime, fuente y policy exactos.
52: 
53: Cargo fix ejecuta build.rs y proc macros dentro de source guest escribible. Ese
54: código puede influir en cualquier byte permitido del candidato; un check exitoso
55: no prueba que cada cambio provenga de una sugerencia del compilador. La revisión
56: del diff exacto, su autorización y la allowlist del publisher delimitan el efecto.
57: 
58: ## Alternatives considered
59: 
60: - Ampliar seccomp global: añade capacidad a operaciones que no la necesitan.
61: - Cargo fix en host: ejecuta código del proyecto fuera de containment.
62: - Reimplementar rustfix y coordinación Cargo: añade un motor semántico y trabajo
63:   de compatibilidad que Cargo ya mantiene.
64: - Instalar un broker o runtime nuevo: coste operacional sin beneficio para este
65:   mecanismo de coordinación dentro del guest existente.
66: - Rechazar fix por cualquier socket: impediría el mecanismo real de Cargo aun
67:   manteniendo la ausencia de conectividad externa.
68: 
69: ## Consequences
70: 
71: La instalación y los cuatro parámetros existentes del sandbox no cambian. Solo
72: se añade el opt-in de escritura de esta operación. El perfil admite coordinación
73: TCP interna para código no confiable; el kernel y aislamiento Docker continúan
74: siendo la frontera. La prueba std-only D06 no acredita workspaces arbitrarios,
75: dependencias offline, código hostil ni todas las salidas del compilador. Esas
76: pruebas y revisión del perfil de producción son necesarias antes de M2-03 Done.
77:

1: # ADR-058 — Observabilidad local de las mutaciones
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: G3 exige observar admisión, rechazos, duración, cancelación, timeout, cleanup y
8: retención. M2 debe cumplirlo sin un colector, servicio, cuenta o configuración
9: adicional. Los resultados y receipts existentes describen la operación, pero no
10: bastan para registrar una cancelación cuya respuesta suprima el cliente.
11: 
12: ## Decision
13: 
14: Emitir como máximo un evento estructurado y acotado de terminación por llamada M2 que pasó decode y conversión del DTO,
15: mediante el tracing/stderr existente. Campos cerrados: tool, fase pública
16: preview/commit/receipt/recover, estado/razón, duración total de trabajo y cleanup (incluido el join cuando el waiter sigue vivo), indicador de cleanup incierto, ID opaco producido cuando exista,
17: archivos cambiados y conteo/bytes de planes asignados. Una llamada rechazada
18: conserva su razón; no se la cuenta como admisión exitosa. El evento no representa
19: la terminación de cada subprocess individual ni un resultado durable perdido.
20: 
21: Si el SDK descarta el waiter por EOF/cancelación, un fallback unido al worker emite después de terminar el trabajo y cleanup; no afirma entrega de respuesta ni mide un join async que ya no existe. Un control de emisión única evita duplicados al competir el retorno normal y el fallback.
22: 
23: Si el waiter se abandona antes de que el worker entre en el trabajo, puede no existir evento de terminación: no se promete auditoría completa de admisión ni entrega ante crash. `admitted` indica entrada al worker sin rechazo de autoridad; no acredita un commit, un mutador ejecutado ni un permiso durable. El estado y razón conservan la distinción de resultado.
24: 
25: No registrar argumentos, referencias del cliente, rutas, source, diffs, Cargo
26: stdout/stderr, variables, credenciales ni idempotency keys. Los IDs solo proceden
27: de resultados validados. Las llamadas que no decodifican conservan el error MCP
28: existente y no registran el payload. No leer RUST_LOG ni habilitar logs del SDK.
29: Los tests de stdio verifican los campos y excluyen cualquier otra salida.
30: 
31: Las métricas son observaciones locales por llamada, no un servidor HTTP ni
32: telemetría externa. Conteo/bytes describen planes aún asignados, incluidos los
33: revocados y terminales retirados que esperan pruning en la próxima admisión; no son RSS ni una medición
34: del journal. La CLI `mutation list` ofrece el inventario durable y cuotas.
35: Diff y resultado excedidos se rechazan completos: no hay cambios omitidos aplicados.
36: 
37: El proceso no crea archivos de logs; su retención pertenece al host que consume
38: stderr. Los receipts permanecen en el store privado autorizado, con borrado
39: explícito conforme a ADR-052. Las fases internas durables y su recuperación se
40: verifican mediante las pruebas nativas y journal, sin exponer paths en logs.

1: # ADR-059 — Liberar planes terminales y repetir desde el journal
2: 
3: Date: 2026-09-05
4: 
5: ## Context
6: 
7: El cliente stock completó cuatro mutaciones y encontró limit_exceeded al preview de
8: la quinta: los planes comprometidos seguían contando en la cuota de cuatro durante
9: 600 s. Esa cuota protege candidatos pendientes; no debe limitar una sesión a cuatro
10: operaciones secuenciales. Eliminar buffers sin otra vía de replay perdería los
11: reintentos tras perder una respuesta, porque commit resolvía siempre un plan RAM.
12: 
13: ## Decision
14: 
15: Retirar un plan de la resolución y marcar su retención liberada solo después de
16: un receipt terminal conocido (Committed, NoChange o Aborted) con su ID y digest.
17: La marca es atómica y no necesita retomar un mutex tras el efecto durable; la próxima
18: admisión poda los buffers antes de aplicar cuotas, igual que los previews no entregados.
19: Cuatro planes activos/64 MiB y TTL 600 s permanecen. Un resultado incierto o error no
20: se interpreta como terminal. No hay cache adicional de receipts ni cuotas ampliadas.
21: 
22: Cuando commit no encuentra un plan RAM válido por ausencia o TTL, puede repetir
23: exclusivamente una operación YA journaled mediante ID, digest e idempotency key
24: exactos. Una nueva operación sigue exigiendo el candidato aprobado no expirado.
25: El port del publisher verifica grant vivo, kind/principal, path e identidad física,
26: locks global/workspace y journal íntegro antes de comparar digest/key. Solo después
27: puede devolver el receipt terminal o usar la recuperación ya existente de ese registro.
28: No se crea un registro nuevo, no se carga candidato del caller y no se revalida
29: Cargo en replay. Un registro legacy v1 terminal puede reescribirse explícitamente
30: en v2 después del binding exacto, como ya hacía commit/recovery; receipt continúa
31: read-only. Esa migración mantiene el presupuesto de crecimiento ya calificado.
32: Un ID ausente no provoca efectos; un digest/key distinto falla Conflict antes de
33: reparación. Un journal dudoso conserva RecoveryRequired. Prune sigue retirando esa
34: protección de replay. Esto también permite retry explícito después de reiniciar el
35: servidor o vencer el TTL, bajo la autoridad actual y con los tres valores exactos.
36: 
37: La registry revalida una referencia viva; tras commit/replay que devuelve resultado
38: o RecoveryRequired la invalida como ya hace commit. Un reference viejo no se convierte
39: en autoridad por conocer ID/key. La tool de otra operación no adquiere acceso.
40: No cambian DTOs, schemas M1, formato journal ni parámetros públicos. Las descripciones
41: de las cinco tools M2 explicitan invalidación y uso del nuevo data.project_ref,
42: además de diferenciar efectos nuevos de replay durable. Las guías
43: explican que TTL limita comenzar efectos nuevos y que la evidencia durable gobierna
44: replay de efectos ya autorizados. Runtime/servicios/instalación no se amplían.
45: 
46: ## Alternatives considered
47: 
48: - Aumentar cuota o esperar TTL: desplaza el fallo y aumenta carga/memoria.
49: - Reiniciar el servidor entre tools: oculta el defecto y empeora Agent DX.
50: - Cache de tombstones/receipts: otra cuota/TTL y duplicación de autoridad durable.
51: - Olvidar sin replay: rompe recuperación de respuesta perdida/idempotencia.
52: - Reejecutar candidato ausente: efecto nuevo sin preview válido, rechazado.
53: 
54: ## Consequences
55: 
56: Cinco o más mutaciones secuenciales pueden continuar dentro de cuotas del journal.
57: Siguen limitados cuatro candidatos pendientes. Replay terminal devuelve evidencia
58: histórica, no certifica que el source actual siga siendo ese after. Recovery de un
59: registro pendiente conserva todas las precondiciones/bytes desconocidos existentes.
60: La ruta nueva exige pruebas nativas de key/digest/root/kind/formato/prune y pruebas
61: MCP de secuencia, respuesta perdida, reopen/restart/TTL, además de revisión independiente.

598: destructivas dentro del grant.
599: 
600: Cada tool exige un permiso host distinto sobre la raíz exacta del workspace:
601: 
602: | Tool | Grant |
603: | --- | --- |
604: | `rust.manifest.patch` | `--allow-manifest-write WORKSPACE_ROOT` |
605: | `rust.fmt.apply` | `--allow-fmt-write WORKSPACE_ROOT` |
606: | `rust.fix.apply` | `--allow-fix-write WORKSPACE_ROOT` |
607: | `rust.dependency.add` | `--allow-dependency-add WORKSPACE_ROOT` |
608: | `rust.dependency.remove` | `--allow-dependency-remove WORKSPACE_ROOT` |
609: 
610: Un grant, `project_ref`, plan o receipt no autoriza otra clase de operación. La
611: raíz debe estar dentro de una `--root` de lectura, el runtime Docker completo debe
612: estar configurado y `--state-root` debe quedar fuera de todas las roots. Los planes
613: vencen a los 600 s y comparten un máximo de cuatro entradas/64 MiB. El diff tiene
614: un límite de 128 KiB; una respuesta que no cabe se rechaza antes de retener el plan.
615: Source y candidato admiten 16 MiB totales, 4096 entradas, 1 MiB por archivo, paths
616: de 100 bytes y profundidad 32. El store admite 128 journals/256 MiB, con 48 MiB
617: por journal y reserva para recovery; al llenarse rechaza trabajo nuevo.
618: 
619: ### Ciclo común preview/commit/receipt
620: 
621: Preview recibe la identidad devuelta por `rust.project.open`, captura y valida un
622: candidato completo, y no modifica el host. Por ejemplo, commit consume exactamente
623: el plan y digest recibidos. `idempotency_key` admite 1–64 caracteres ASCII
624: alfanuméricos, guion o underscore:
625: 
626: ```json
627: {
628:   "project_ref": "prj_0123456789abcdef0123456789abcdef",
629:   "action": {
630:     "mode": "commit",
631:     "plan_id": "mut_0123456789abcdef0123456789abcdef",
632:     "plan_digest": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
633:     "idempotency_key": "agent-step-17"
634:   }
635: }
636: ```
637: 
638: Tras commit se debe reabrir el proyecto y usar el nuevo `data.project_ref` en
639: TODAS las llamadas posteriores, incluidos receipt y recovery del `operation_id`. `recover: true` solicita recuperación conservadora; el ID por sí mismo
640: no concede acceso:
641: 
642: ```json
643: {
644:   "project_ref": "prj_fedcba9876543210fedcba9876543210",
645:   "action": {
646:     "mode": "receipt",
647:     "operation_id": "mut_0123456789abcdef0123456789abcdef",
648:     "recover": false
649:   }
650: }
651: ```
652: 
653: Preview devuelve `kind: "preview"`, plan, expiración, lista de archivos, diff y
654: validación. Receipt devuelve estado `committed`, `no_change`, `aborted` o
655: `recovery_required`, fingerprints de efecto y la validación ligada al plan. La
656: semántica de evidencia es `latest_known`: un receipt no es una lectura actual del
657: filesystem. Un candidato rechazado por Cargo es un resultado `failed`; conflictos,
658: permisos, plan vencido, recovery y datos offline ausentes son resultados
659: operacionales con `isError: true`. La ausencia de dataset/crate offline es `unavailable` con `offline_data_missing`; datos adulterados son `blocked` con `offline_data_invalid`.
660: 
661: El modo es `local_coordinated`. El commit vuelve a comprobar proyecto y source y
662: publica los bytes aprobados mediante handles no-follow y journal. Los locks
663: coordinan instancias que comparten state root; no excluyen al IDE, Git u otros
664: writers. No hay CAS ni atomicidad visible multiarchivo. Los cambios externos pueden
665: causar `conflict` o `recovery_required`.
666: 
667: La CLI `mutation list/prune` administra journals terminales, pero el checkout no
668: incluye un updater o downgrade gestionado. Los journals pendientes deben
669: reconciliarse antes de ejecutar un binario anterior; `0.1.0` no conoce su formato.

671: ### `rust.manifest.patch`
672: 
673: Solo edita el `Cargo.toml` raíz mediante una operación semántica. Ejemplo de profile:

704: flags Cargo. El manifest se limita a 256 KiB y un no-op conserva sus bytes.

706: `line-tables-only` o `line-directives-only`; `strip` acepta `none`, `debuginfo` o

708: `debug-assertions`, `overflow-checks` e `incremental` son booleanos, y
709: `codegen-units` es un entero mayor o igual a uno.
