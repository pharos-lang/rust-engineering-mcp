# ADR-048 — 0.1.0 qualification and artifact boundary

## Status

Accepted by the Technical Owner on 2026-09-04 for M1 closure. This decision does
not authorize M2 work, an official catalog, model redistribution, or crates.io.

## Context

The M1 implementation and its full local gate include SQLite/FTS5, the derived
LanceDB index and the local E5 provider. The only positive protected-filesystem
host is macOS 26 ARM64 on APFS; external Cargo execution is contained in the
separately calibrated Docker Linux ARM64 gateway. Public CI also proves portable
source, protocol and fail-closed behavior on Linux x86_64 and Windows x86_64, but
those hosts do not have protected-I/O adapters and cannot run the positive M1
project or catalog flows.

The existing release workflow builds core binaries without the `local` feature.
That profile excludes E5, ORT and LanceDB, so it cannot by itself qualify the M1
product. Conversely, publishing the current local-feature review bundle would
redistribute an E5 model without a separate license text, a static ORT archive
without a complete build-to-notice receipt and a Kanaria dependency whose crate
archive has only a manifest declaration. The catalog fixture uses a public test
key and cannot become a production trust root.

M1 needs a truthful release boundary that preserves the implemented contract and
security posture without presenting unqualified platforms or third-party assets as
supported.

## Decision

The fully qualified M1 host profile for 0.1.0 is macOS 26 ARM64 on APFS, with the
approved Docker Linux ARM64 gateway for all project-code execution. Linux x86_64
and Windows x86_64 remain source-portability and fail-closed CI targets; they are
not positive project/catalog capability targets. No Linux ARM64, macOS x86_64 or
Windows ARM64 artifact is advertised for 0.1.0. Adding a positive host profile
requires its protected-I/O adapter, native security oracles and a new qualification
receipt; green compilation is insufficient.

The initial GitHub Release contains one macOS ARM64 **core** archive. It includes
the executable, product license files, a target-specific dependency inventory, a
machine-readable SBOM, third-party notices, hashes and GitHub OIDC provenance. It
contains no model, ORT runtime, LanceDB data, catalog, catalog trust file, fixture,
Docker image or toolchain. Installation, `version`, passive `doctor`, protocol
discovery, the exact thirteen-tool inventory and expected structured degraded/error
paths are tested from the archive. The release documentation must state that this
artifact alone provides the stable MCP contract and offline lexical/degraded paths,
not the complete local semantic profile or project execution runtime.

The `local` feature remains part of M1 and is not deferred to M2. Product closure is
a compound gate: the core archive gates above **and** a fresh source-bound full gate
on the qualified host with exact E5/ORT inputs, real SQLite/FTS5/LanceDB semantic
search, the Docker execution gateway, all thirteen tools, Resources and clients.
Therefore a core build alone still cannot qualify M1. Users who build `local` must
provision the exact compatible E5 and ORT inputs themselves and accept their
licenses; 0.1.0 does not redistribute or support those bytes as a release artifact.

IUMotion Labs will not publish an official catalog in 0.1.0. Catalog import,
signature verification, antirollback, rotation-by-host-key-change and revocation by
trust removal remain implemented and tested. The release ships no catalog endpoint,
private key, public production key or fixture bundle. Consequently there is no
production Ed25519 key to custody for this release. A future official catalog is a
new distribution decision requiring an operational key procedure, source/terms
review, notices and a separately signed artifact.

GitHub remains the source and binary channel and crates.io remains disabled. This
decision narrows only release artifacts and positive host claims; the public MCP
contract remains exactly thirteen tools and unsupported capabilities continue to
fail closed.

For the already published vendored LanceDB source, the Technical Owner accepts the
Apache-2.0 applicability evidence at exact Cargo VCS revision
`3f8d76817e6020ea344fba8a66c5de9ad8c82234`: the upstream `rust/lancedb`
manifest declares `Apache-2.0`, the repository-root license bytes and Git blob are
verified at that same revision, and no narrower subtree license is present. The
request/redirect/blob/hash chain is retained in
`docs/release/upstream-licenses/receipt.json`; `scripts/verify-vendor.py` pins those
bytes. This is an engineering distribution decision, not a representation of legal
advice. LanceDB still does not enter the 0.1.0 core binary closure or archive.

## Alternatives considered

- Implement Linux and Windows protected-I/O and sandbox adapters before 0.1.0. This
  preserves the broadest platform goal but is a distinct security program and would
  delay a truthful first release; portable runners cannot substitute for it.
- Publish the local-feature binary and model. Rejected because the current third-
  party and native provenance is insufficient for redistribution.
- Remove semantic search from M1. Rejected because it is implemented, independently
  tested and remains part of the compound source qualification.
- Use the public fixture catalog/key as an example release. Rejected because the key
  is deliberately forgeable and would blur the production trust boundary.
- Publish core binaries for Linux and Windows as supported products. Rejected because
  `rust.project.open` and the protected catalog store intentionally fail closed there.

## Consequences

The supported binary matrix is intentionally small but precise. Documentation must
separate source portability, fail-closed behavior, positive native capability and
artifact qualification. M1-15 can close without resolving Kanaria, E5 or ORT
redistribution because none enters the published archive; their declarations and
limitations remain visible for source builders. Catalog-key operations no longer
block 0.1.0 because no official catalog is shipped.

The release pipeline must reject extra targets/assets, generate and validate the
core artifact inventory/SBOM/notices, install from the archive, run the artifact
smoke, attest it and verify the attestation. The final M1 gate must still exercise
the complete local profile on the qualified host. Linux/Windows positive support,
local-feature binary distribution and official catalogs require later explicit
decisions; none is silently promised by 0.1.0.
